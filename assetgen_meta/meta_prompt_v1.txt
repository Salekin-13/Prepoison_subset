TASK
Design a methodology that a separate LLM (the executor) will follow to analyze the elements (interface ports and internal signals) of one hardware IP module and determine which of them are PRIMARY ASSETS for pre-silicon security verification under the CONCEPTUAL-and-STRUCTURAL ANALYSIS (CSA). Then write the execution prompt that makes the executor apply that methodology.

HOW TO READ THIS PROMPT
Sections marked [FIXED] contain definitions and rules. Carry them into the methodology and into the execution prompt without weakening, narrowing, or rewording their meaning. Sections marked [OPEN] are for you to design.

INPUT OF THE EXECUTION PROMPT [FIXED]
This meta prompt receives no RTL. The executor will receive only the RTL of one hardware IP module, with all comments removed. The RTL may declare more than one entity. The RTL is the sole authoritative source for the analysis. The execution prompt must not treat comments as a source of evidence, because the input has none.

DEFINITIONS [FIXED]
- Two axes. Assets are classified along two independent axes: abstraction (conceptual vs structural, from IEEE P3164) and dependency (primary vs secondary, from SAIF).
- Conceptual asset: a piece of data, configuration, or system state (including a decision or event the module computes) that a use-case flow of the IP depends on, and whose confidentiality, integrity, or availability must hold for that flow to be secure. It is defined by what it means, not where it is. It must be identifiable from the RTL as a value the module produces, stores, or uses.
- Structural asset (structural reference): a declared RTL element (a port, a signal, or a field of an internal record signal) that realizes a conceptual asset: where its value is stored, set, or computed, or the port through which it leaves its entity. An element that only passes the value along, or gates it on the way, carries the asset but is not its structural reference. One conceptual asset usually has several structural references along its path, and one element can realize several conceptual assets.
- Primary asset: a primary asset is an element that stores, sets, or computes a security-relevant value or decision, or a port through which such a value leaves its entity. Elements that only pass the value along or gate it between those points are not primary, but secondary assets. At module level, the primary assets are the structural references of the conceptual assets. These are what the executor reports.
- Secondary asset: an element that only passes a primary asset's value along or gates it between those points, or an internal signal or register that influences a primary asset or could violate its security objective. The executor never reports secondary assets; a later stage finds them from connectivity.
- Use-case flow: an operation the RTL implements, such as configuring the module, starting an operation, computing a result, reporting status, or reading out data.
- Closed set (candidate universe): the declared ports of every entity in the RTL, the declared internal signals, and the individually identifiable fields of internal record signals. Nothing else can be a structural asset.
- Evidence levels:
  Established: the RTL explicitly or logically establishes that the value, state, or decision has a confidentiality, integrity, or availability property that matters to a module operation or flow.
  Context-dependent: the RTL identifies a meaningful value, state, or decision, but whether its security matters depends on information outside the RTL.
  Insufficient evidence: the RTL does not provide enough information to establish the conceptual meaning or the security property.
- Information categories:
  Explicit information: directly represented in the RTL, including declared ports, signals, fields, types, widths, element names, assignments, state elements, state transitions, and explicit operations or comparisons.
  RTL-derived information: not stated directly but logically established from the RTL, such as a value being stored in a register, computed from particular inputs, controlling a state transition, propagating to a particular output, or determining another state or value.
  External/contextual information: requires knowledge beyond the RTL, such as system architecture, application purpose, designer intent, software or firmware behavior, deployment environment, threat model, unstated security requirements, or how a signal is used outside the module.

OUTPUT OF THIS PROMPT [FIXED]
Return plain text with exactly two parts, each starting with its marker line:
=== METHODOLOGY ===
The methodology specification, with one numbered section for each of the eleven METHODOLOGY SECTIONS below, in the same order and with the same titles.
=== EXECUTION PROMPT ===
The complete system prompt for the executor, ready to use as is. It must be self-contained, apply the methodology, include the DEFINITIONS above, and include the EXECUTOR OUTPUT SCHEMA below verbatim.
Return nothing before the first marker. Do not return an asset list or JSON for any module.

METHODOLOGY SECTIONS

1. Information [FIXED]
The executor distinguishes the three information categories defined above. Only explicit and RTL-derived information may be used to classify an asset. External/contextual information is never silently converted into an RTL fact. If the security relevance of an element depends on unavailable external information, that dependency is treated as Context-dependent, not assumed. The analysis answers, in order: what is explicitly present in the RTL; what can be logically established from it; what remains unknown because it needs external context.

2. Observation [FIXED rules; OPEN method]
The executor first builds the closed set, recording for each element its exact declared name and the entity that declares it. Expressions, assignments, operators, processes, functions, procedures, state transitions, conditions, and similar constructs are not assets; they are evidence about declared elements. The executor derives relationships from the RTL before classifying anything, and distinguishes a value's origin or realization point from the intermediate elements it later travels through.
[OPEN] Define which properties may be derived from the RTL, and which forms of data-flow, control-flow, state, dependency, or structural analysis are appropriate. The output of this stage is a set of RTL-derived relationships connecting elements to values, decisions, states, computations, and outputs.

3. Use-case flows [FIXED requirement; OPEN method]
Before identifying conceptual assets, the executor derives the module's use-case flows from the RTL alone.
[OPEN] Define how flows are recognized from the RTL, and how each flow is described so that the next stage can use it.

4. External information [OPEN]
Define which conclusions need information outside the RTL, and how the executor handles them without unsupported assumptions. The executor never invents missing information.

5. Asset definition [FIXED]
Apply the DEFINITIONS. Conceptual assets are identified first, from the use-case flows; their structural references are identified second. The analysis never starts by labeling individual signals as assets. A conceptual asset is reported only when its evidence level is Established.

6. Security relevance [OPEN]
Define how the executor decides, from permitted evidence only, whether a conceptual asset's confidentiality, integrity, or availability matters, and how it tells explicit relevance, RTL-derived relevance, and Context-dependent relevance apart. Security relevance is tied to one or more of:
- Confidentiality: unauthorized disclosure of the value would violate a property established from the RTL.
- Integrity: unauthorized modification, corruption, or incorrect setting of the value or decision would violate a property established from the RTL.
- Availability: preventing the value, state, decision, or event from being produced, maintained, or delivered would violate a property established from the RTL.
The executor avoids generic assumptions such as "all configuration is sensitive" or "all control signals are security-critical".

7. Evidence sufficiency [FIXED rules; OPEN detail]
Every classification is supported by evidence from the RTL. Evidence is an explicit RTL fact or a conclusion that follows logically from identified RTL relationships; inference is an interpretation the RTL does not establish. A sufficient chain for an Established conceptual asset connects: RTL evidence, then an identifiable value, state, or decision, then its security significance, then its confidentiality, integrity, or availability objective. Element names may support interpretation but are corroborated by RTL behavior when security relevance is not explicit. Conflicting evidence is resolved conservatively; incomplete evidence leads to Context-dependent or Insufficient evidence, never to speculative completion.
[OPEN] Define what counts as sufficient evidence in more detail, how evidence is told apart from inference, and how conflicting or incomplete evidence is handled.

8. Uncertainty [FIXED]
The executor uses the three evidence levels defined above, with exactly those names. Uncertainty is never resolved by assuming common hardware-security conventions. Only Established conceptual assets, and their structural references, appear in the output. Context-dependent and Insufficient evidence cases are decided during the analysis and are not reported. Not established is not the same as not present: failing to establish relevance is not evidence that an element is irrelevant.

9. Analysis procedure [FIXED order and output behavior; OPEN detail]
The stages run in this order: build the closed set; derive relationships; derive use-case flows; identify conceptual assets; identify their structural references; validate.
The executor starts from the empty output object:
{"module name": "", "conceptual assets": []}
When it identifies conceptual assets, it fills in "module name" and adds one entry per Established conceptual asset, with "related structural assets" left empty. When it moves on to structural references, it fills in each "related structural assets" list. It then validates the object. This filling happens during the analysis; the response contains only the final, completed object.
[OPEN] For each stage, define its purpose, input, operation, and output, and the dependencies between stages.

10. Validation [OPEN]
Define how each reported asset and its security relevance are checked against the RTL, including checks for unsupported assumptions, incomplete evidence, and inconsistencies. At minimum, each "asset rtl" must be an exact name from the closed set, each "entity" must be the entity that declares it, and no carrier may be reported as a structural reference.

11. Output representation [FIXED]
The executor returns the EXECUTOR OUTPUT SCHEMA below and nothing else.

EXECUTOR OUTPUT SCHEMA [FIXED]
Return ONE JSON object and nothing else: no markdown, no code fences, no prose. Use the keys exactly as written.
{"module name": "<the module analysed>",
 "conceptual assets": [
   {"concept": "<the conceptual asset identified>",
    "security objective": "Confidentiality" | "Integrity" | "Availability",
    "reasoning": "<how it was considered an asset, grounded in the RTL>",
    "related structural assets": [
      {"asset rtl": "<exact declared name from the closed set; a field of an internal record signal is written with its dot, as declared>",
       "entity": "<the entity that declares the element, copied verbatim>",
       "realization": "stores" | "sets" | "computes" | "exit port"}
    ]}
 ]}
If the module has no Established conceptual assets, return {"module name": "<the module analysed>", "conceptual assets": []}.

DESIGN CONSTRAINTS [FIXED]
The methodology and the execution prompt must:
- Be reusable across arbitrary RTL designs and independent of any particular RTL instance.
- Be evidence-driven, and clearly distinguish observation, logical derivation, and contextual assumption.
- Avoid inferring security relevance solely from generic real-world expectations, and identify information gaps explicitly.
- Be precise enough that the executor applies them consistently.
- Keep asset identification separate from vulnerability discovery, exploitability analysis, and threat assessment, unless a dependency is needed to define asset relevance.
- Contain no quantities, quotas, thresholds, or percentages about how many assets, concepts, or elements to report.
- Contain no names of real designs, modules, or signals. If an illustration is unavoidable, use an obviously invented name.
- Contain no example analysis of any RTL.
- Specify the decisions and evidence the executor must produce, without asking it to expose private chain-of-thought. The executor is a reasoning model.
