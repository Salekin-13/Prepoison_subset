=== METHODOLOGY ===

1. Information

The executor distinguishes the three information categories defined below. Only explicit and RTL-derived information may be used to classify an asset. External/contextual information is never silently converted into an RTL fact. If the security relevance of an element depends on unavailable external information, that dependency is treated as Context-dependent, not assumed. The analysis answers, in order: what is explicitly present in the RTL; what can be logically established from it; what remains unknown because it needs external context.

The executor receives only the RTL of one hardware IP module, with all comments removed. The RTL may declare more than one entity. The RTL is the sole authoritative source. Comments are not a source of evidence.

Maintain a distinction between:
- Observed declarations and behavior.
- Conclusions logically supported by those observations.
- Interpretations requiring unavailable context.

Use concise evidence summaries in the final output, not private chain-of-thought, intermediate deliberations, or an analysis transcript.

2. Observation

The executor first builds the closed set, recording for each element its exact declared name and the entity that declares it. Expressions, assignments, operators, processes, functions, procedures, state transitions, conditions, and similar constructs are not assets; they are evidence about declared elements. The executor derives relationships from the RTL before classifying anything, and distinguishes a value's origin or realization point from the intermediate elements it later travels through.

Build the candidate inventory from every entity in the supplied RTL:
- Record declared ports as whole elements, including their directions.
- Record declared internal signals.
- Resolve internal record types sufficiently to identify their declared fields and field paths.
- Keep declaring-entity identity separate from the element name.
- Do not introduce variables, constants, parameters, expressions, array selections, process labels, or instance paths as additional candidates.
- If a referenced type is unavailable, do not invent its fields.

Record relevant declaration properties: type, width, direction, record membership, retained or combinational behavior, drivers, readers, reset or initialization assignments, and entity boundaries.

Derive relationships using:
- Data flow: assignments, transformations, selections, register reads and writes, value propagation, and output connections.
- Control flow: conditions, comparisons, case alternatives, enables, acceptance or rejection paths, and the assignments they control.
- State analysis: retained values, next-state relationships, initialization, updates, completion conditions, and state-dependent behavior.
- Dependency analysis: which values influence a computation, state transition, decision, or output, and under what conditions.
- Structural analysis: entity instances, bindings visible in the RTL, port connections, internal record connections, and transaction-shaped interfaces.

Preserve distinctions between storing a value, establishing a new value, computing a value or decision, consuming an input locally, exporting a value, and merely transporting or gating an existing value.

Analyze procedures and functions only to establish their effects on declared candidates and flows. Do not report the procedure, function, call, predicate, or assignment itself.

Use elaboration information established by the supplied RTL. Preserve parameter conditions and alternative branches where elaboration is unresolved. Do not invent missing component behavior, type definitions, bindings, or environmental guarantees.

The result is a set of RTL-derived relationships connecting declared elements to identifiable values, decisions, states, computations, and outputs. This stage does not label elements as assets.

3. Use-case flows

Before identifying conceptual assets, the executor derives the module's use-case flows from the RTL alone.

Recognize flows from coherent operations implemented by related input consumption, state updates, computations, decisions, and observable results. A flow may be continuously active, combinational, transaction-driven, or stateful; an explicit start signal or state machine is not required.

For each flow, record:
- The operation demonstrated by the RTL.
- Its initiating conditions or continuous operating conditions.
- Inputs and existing state consumed.
- Computations, decisions, and state changes performed.
- Results, status, events, or state produced.
- Completion, delivery, or externally visible behavior, where present.
- Conditions that constrain its operation.
- Boundaries beyond which behavior is not available in the supplied RTL.

Describe the flow semantically but without inventing an application, software sequence, user identity, or system-level purpose. Names may help describe a flow only when its behavior corroborates the description.

Keep entity boundaries visible. A sub-block connection demonstrates a connection, not the unavailable behavior of that sub-block. A locally implemented flow in another supplied entity may be analyzed, but its participation in a larger flow requires a visible relationship.

The output is a flow inventory supported by the relationships from Observation. Conceptual asset identification starts from this inventory, not from a list of suggestively named signals.

4. External information

Conclusions requiring external information include:
- Whether a value is secret merely because of its name or presumed application.
- Whether an interface connects to a trusted or untrusted component.
- Whether a source identifier denotes a security principal outside the module.
- How software programs configuration or interprets results.
- Whether a deployment requires a particular latency, throughput, retention period, or policy.
- Whether an adversary can control a signal or exploit a condition.
- Behavior of missing entities, packages, firmware, or system components.
- Designer intent, unstated requirements, and environmental progress guarantees.

Do not supply these facts from common hardware-security conventions.

When a meaningful value or decision is established but its security relevance requires such a fact, classify the conceptual candidate as Context-dependent. When the RTL cannot establish its meaning or a supportable security property, classify it as Insufficient evidence.

An unresolved external dependency does not invalidate unrelated local facts. Retain supported local and conditional conclusions without extending them beyond the RTL boundary.

Do not turn asset identification into vulnerability discovery, exploitability analysis, or threat assessment. A counterfactual change to a value may establish its importance to an RTL-defined property without establishing an attack mechanism.

5. Asset definition

Apply the following definitions without changing either classification axis.

DEFINITIONS

- Two axes. Assets are classified along two independent axes: abstraction (conceptual vs structural, from IEEE P3164) and dependency (primary vs secondary, from SAIF).
- Conceptual asset: a piece of data, configuration, or system state (including a decision or event the module computes) that a use-case flow of the IP depends on, and whose confidentiality, integrity, or availability must hold for that flow to be secure. It is defined by what it means, not where it is. It must be identifiable from the RTL as a value the module produces, stores, or uses.
- Structural asset (structural reference): a declared RTL element (a port, a signal, or a field of an internal record signal) that realizes a conceptual asset: where its value is stored, set, or computed, or the port through which it leaves its entity. An element that only passes the value along, or gates it on the way, carries the asset but is not its structural reference. An input port whose value this entity itself reads, to store it, compute from it, or decide on it, is where that value enters the entity: it is a structural reference of the concept it carries, with realization "sets". Clock, clock-enable and reset inputs are not structural references in this way, unless controlling a clock or a reset is this block's function, in which case they are (clock and reset are security concerns: CWE-1206). A port whose record type carries complete bus transactions is governed by the Transport definition instead. One conceptual asset usually has several structural references along its path, and one element can realize several conceptual assets.
- Primary asset: a primary asset is an element that stores, sets, or computes a security-relevant value or decision, or a port through which such a value leaves its entity. Elements that only pass the value along or gate it between those points are not primary, but secondary assets. An input port whose value this entity itself reads, to store it, compute from it, or decide on it, is where that value is set. At module level, the primary assets are the structural references of the conceptual assets. These are what the executor reports.
- Secondary asset: an element that only passes a primary asset's value along or gates it between those points, or an internal signal or register that influences a primary asset or could violate its security objective. The executor never reports secondary assets; a later stage finds them from connectivity.
- Transport: a port or signal whose record type carries complete read or write transactions between this block and an interconnect is transport for its payload: the address, write data, byte enables, strobe, acknowledge and read data. The payload is not a primary asset: do not report it, whole or by field. Do not use a transport element as the exit of a value that a register holds and software can read back, or as the element that sets a value written into this block; report the element inside the block that stores or decides the value. A security attribute carried with a transaction is different: a privilege level, a debug-mode flag, or a source or initiator identifier (the concern of CWE-1302, CWE-1311, CWE-1317 and CWE-1318). When this block decides on such an attribute, for example to allow, deny, bypass or route an access, that access-control decision is a conceptual asset. Its structural reference is the internal element that computes or stores the decision; if the decision is taken directly on the attribute, with no internal element holding it, the structural reference is the transaction port, named whole. An attribute that is only passed along unchanged is carried, not decided. A port is a single candidate: name it whole; never report a field of a port.
- Sub-block connection field: a field of an internal record that only connects this block to an instantiated sub-block, receiving one of its outputs or passing a value unchanged to one of its inputs, is a carrier. Do not report it unless this block tests it in an if, case or when condition, or computes it here from a decision.
- Use-case flow: an operation the RTL implements, such as configuring the module, starting an operation, computing a result, reporting status, or reading out data.
- Closed set (candidate universe): the declared ports of every entity in the RTL, the declared internal signals, and the individually identifiable fields of internal record signals. A port is a single candidate; its fields are not candidates. Nothing else can be a structural asset.
- Evidence levels:
  Established: the RTL explicitly or logically establishes that the value, state, or decision has a confidentiality, integrity, or availability property that matters to a module operation or flow.
  Context-dependent: the RTL identifies a meaningful value, state, or decision, but whether its security matters depends on information outside the RTL.
  Insufficient evidence: the RTL does not provide enough information to establish the conceptual meaning or the security property.
- Information categories:
  Explicit information: directly represented in the RTL, including declared ports, signals, fields, types, widths, element names, assignments, state elements, state transitions, and explicit operations or comparisons.
  RTL-derived information: not stated directly but logically established from the RTL, such as a value being stored in a register, computed from particular inputs, controlling a state transition, propagating to a particular output, or determining another state or value.
  External/contextual information: requires knowledge beyond the RTL, such as system architecture, application purpose, designer intent, software or firmware behavior, deployment environment, threat model, unstated security requirements, or how a signal is used outside the module.

Conceptual assets are identified first, from the use-case flows; their structural references are identified second. The analysis never starts by labeling individual signals as assets. A conceptual asset is reported only when its evidence level is Established.

Describe each concept as a meaningful value, configuration, state, decision, or event. Do not define it merely as a signal name or as “everything influencing” another asset.

During structural mapping:
- Apply the transport and sub-block connection rules before treating connectivity as realization.
- Interpret “sets” as value establishment, not simply appearance on the left side of an assignment.
- Do not turn an unchanged internal copy into a realization by calling the copy an assignment.
- Distinguish a decision from the data path it gates.
- Treat local testing of a sub-block connection field as eligibility under the exception, not automatic proof of an Established concept.
- Associate the same declared element with different concepts when the RTL supports those distinct meanings.

6. Security relevance

For each flow-derived conceptual candidate, formulate the particular RTL-grounded property that would need to hold. Then evaluate the applicable objectives:

- Confidentiality: unauthorized disclosure of the value would violate a property established from the RTL.
- Integrity: unauthorized modification, corruption, or incorrect setting of the value or decision would violate a property established from the RTL.
- Availability: preventing the value, state, decision, or event from being produced, maintained, or delivered would violate a property established from the RTL.

Identify the concrete relationship between the candidate and that property. Relevant evidence may include:
- A restriction on observation or release of a value.
- A comparison or decision governing acceptance, denial, bypass, or routing.
- A computation whose result represents the flow's implemented result.
- Configuration or state determining an implemented operation.
- A validity, consistency, completion, status, or delivery relationship.
- Retention or production of a value needed for a demonstrated operation.

These are evidence patterns, not automatic classifications.

Explicit relevance exists when the RTL directly represents the relevant restriction, decision, or required relationship. RTL-derived relevance exists when the candidate's role and the consequence of changing, disclosing, or withholding it follow from identified relationships.

Do not require a security-themed name or a dedicated protection mechanism. Integrity or Availability may be established for an ordinary operation when the RTL demonstrates a specific value, state, result, or event that operation depends on and a concrete property its corruption or absence would violate.

Conversely, mere fan-out, connectivity, storage, change in behavior, or presence in a control cone does not establish a conceptual asset. Explain what meaningful property of which flow is at stake. Do not assume that all configuration is sensitive or all control signals are security-critical.

Confidentiality requires an RTL-grounded disclosure property; storage, encoding, or a suggestive name alone does not establish secrecy. Availability claims must respect environmental conditions: do not infer unconditional progress from a flow that depends on unspecified external readiness or activity.

Security relevance concerns the property that matters, not proof that the implementation successfully protects it. Do not infer exploitability or an adversary's capabilities.

If several objectives are Established for the same concept, retain the concept as a single entry. For the scalar “security objective” field, select Confidentiality, then Integrity, then Availability among the Established objectives. This is a formatting tie-break, not a severity ranking. State the other Established objectives and their support in “reasoning”; do not duplicate a concept merely to represent objectives.

7. Evidence sufficiency

Every classification is supported by evidence from the RTL. Evidence is an explicit RTL fact or a conclusion that follows logically from identified RTL relationships; inference is an interpretation the RTL does not establish. A sufficient chain for an Established conceptual asset connects: RTL evidence, then an identifiable value, state, or decision, then its security significance, then its confidentiality, integrity, or availability objective. Element names may support interpretation but are corroborated by RTL behavior when security relevance is not explicit. Conflicting evidence is resolved conservatively; incomplete evidence leads to Context-dependent or Insufficient evidence, never to speculative completion.

For each conceptual candidate, check:
- Meaning: the RTL identifies what value, state, decision, or event is involved.
- Flow relationship: the flow demonstrably consumes, produces, maintains, or depends on it.
- Property: the RTL supports a particular confidentiality, integrity, or availability requirement for that relationship.
- Consequence: violation of the requirement has a traceable consequence for the demonstrated flow.
- Scope: the conclusion stays within visible entities, conditions, and behavior.

For each structural reference, additionally check its declaration, declaring entity, value relationship, realization role, and applicable exclusions.

A source-grounded evidence summary should identify the relevant assignments, comparisons, state updates, or use relationships. Signal names alone and generic claims such as “security-critical” are insufficient.

Inspect conditional paths, overwrites, initialization, competing drivers, and alternative uses that may contradict a proposed interpretation. Narrow a claim to supported conditions when justified. Otherwise classify it as Context-dependent or Insufficient evidence, according to the missing link.

Do not confuse absence of an enforcement mechanism with absence of security relevance. Also do not claim an enforcement guarantee when the RTL contradicts it.

Unavailable structural declarations do not authorize invented references. Evidence for a conceptual asset and eligibility of a structural candidate are separate questions.

8. Uncertainty

The executor uses the three evidence levels defined above, with exactly those names. Uncertainty is never resolved by assuming common hardware-security conventions. Only Established conceptual assets, and their structural references, appear in the output. Context-dependent and Insufficient evidence cases are decided during the analysis and are not reported. Not established is not the same as not present: failing to establish relevance is not evidence that an element is irrelevant.

Maintain uncertainty decisions during analysis without adding uncertainty fields, rejected-candidate lists, or unsupported concepts to the final object.

9. Analysis procedure

The stages run in this order: build the closed set; derive relationships; derive use-case flows; identify conceptual assets; identify their structural references; validate.

The executor starts from the empty output object:
{"module name": "", "conceptual assets": []}

When it identifies conceptual assets, it fills in "module name" and adds one entry per Established conceptual asset, with "related structural assets" left empty. When it moves on to structural references, it fills in each "related structural assets" list. It then validates the object. This filling happens during the analysis; the response contains only the final, completed object.

Stage: build the closed set
- Purpose: establish the only eligible structural candidates.
- Input: supplied RTL.
- Operation: inventory declarations, entities, ports, internal signals, and resolvable internal record fields.
- Output: the closed set with exact names, declaration ownership, and declaration evidence.

Stage: derive relationships
- Purpose: establish behavior without classifying assets.
- Input: RTL and the closed set.
- Operation: perform the data-flow, control-flow, state, dependency, and structural analyses in Observation.
- Output: relationships identifying realizations, local consumption, propagation, gating, transport, and entity crossings.

Stage: derive use-case flows
- Purpose: identify operations that give values their meaning.
- Input: RTL-derived relationships.
- Operation: assemble coherent operations with conditions, consumed state, behavior, and results.
- Output: the flow inventory and its boundaries.

Stage: identify conceptual assets
- Purpose: establish security-relevant meanings before selecting structures.
- Input: flow inventory and supporting evidence.
- Operation: identify conceptual candidates, evaluate objectives and evidence levels, consolidate synonymous concepts, and add only Established concepts to the working object.
- Output: conceptual entries with evidence-grounded reasoning and empty structural lists.

At this stage, determine the reporting module name from the supplied RTL. Use an unambiguously identified top entity when available. Otherwise use the unique entity not instantiated by another supplied entity. If the RTL does not identify a unique root, use the first root in source order, or the first declared entity if there is no identifiable root, solely as a deterministic reporting label. This fallback does not establish system architecture or exclude other entities from the closed set or analysis.

Stage: identify structural references
- Purpose: locate eligible realizations of Established concepts.
- Input: conceptual entries, closed set, and derived relationships.
- Operation: trace each concept to its storage, setting, computation, and eligible exit points; apply all exclusions and special rules.
- Output: populated “related structural assets” lists.

Use realization labels as follows:
- “stores”: the element retains the conceptual value or state.
- “sets”: the element establishes the value without being only a carrier, including a locally consumed input and the permitted whole-transaction-port case.
- “computes”: the element holds a value or decision computed here.
- “exit port”: the concept leaves through that entity's output-capable port, subject to the transport exclusion.

For an eligible output port, use “exit port” to represent its exit role. For an internal retained value, use “stores”; otherwise distinguish computation from setting by the observed behavior. Do not create duplicate references merely to describe the same realization in different words.

If an Established concept has no eligible structural reference in the closed set, do not invent a candidate, promote a carrier, or demote the concept solely for that reason. Leave its structural list empty and explain the absence of an eligible declared reference concisely in its reasoning.

Stage: validate
- Purpose: ensure that only supported concepts and primary structural references remain.
- Input: completed working object, RTL, inventory, and relationships.
- Operation: perform the checks in Validation and repair unsupported or inconsistent entries.
- Output: the final object in the required schema.

Later stages may correct an earlier conclusion when contradictory evidence is discovered, but must not bypass the conceptual-before-structural order.

10. Validation

Validate every reported concept:
- Its meaning is identifiable in the RTL.
- Its use-case flow was derived from RTL behavior.
- Its evidence level is Established.
- Its selected objective is supported by a specific property and consequence.
- Its reasoning does not depend on comments, presumed deployment, names alone, or invented environmental behavior.
- Any conditions or boundaries necessary to the claim are respected.
- Protection efficacy, exploitability, and security relevance have not been conflated.

Validate every structural reference:
- “asset rtl” is an exact name from the closed set.
- “entity” is copied verbatim from the entity declaring that element.
- The name is bare: no entity prefix, instance hierarchy, invented alias, or synthetic expression.
- An internal record field uses its declared record-signal name and declared field path with dots; this is not an entity qualification.
- No port field is reported.
- Its realization label is supported by its behavior for the associated concept.
- A locally consumed input is distinguished from an input merely passed to another entity.
- Clock, clock-enable, and reset inputs obey their stated exception.
- No carrier is reported as a structural reference.
- No transport payload is reported, whole or by field.
- A transaction port is reported only as the structural reference of an access-control decision taken directly on one of its security attributes, with no internal element holding the decision.
- An unchanged security attribute is not treated as a decision.
- A sub-block connection field satisfies the stated local-test or local-computation exception and independently qualifies as a realization of the concept.
- Influence on a primary asset is not mistaken for realization of that asset.

Check that an internal record field and its parent signal have not been redundantly included merely to describe the same realization. Retain distinct supported references and distinct supported conceptual meanings.

If bare names collide in different declaration scopes, do not fabricate qualified “asset rtl” names; use declaration ownership and concise reasoning to preserve the relevant distinction.

Validate the final representation:
- All supplied entities were considered in the closed set.
- Conceptual entries are not duplicates caused by signal aliases or objective formatting.
- Structural lists contain no unsupported additions.
- Only the prescribed keys and enum values are used.
- The final response is a JSON object, not an analysis transcript.
- An empty conceptual list means that no conceptual asset was Established, not that the design has no security concerns.

The executor returns the EXECUTOR OUTPUT SCHEMA below and nothing else.

EXECUTOR OUTPUT SCHEMA

Return ONE JSON object and nothing else: no markdown, no code fences, no prose. Use the keys exactly as written.
{"module name": "<the module analysed>",
 "conceptual assets": [
   {"concept": "<the conceptual asset identified>",
    "security objective": "Confidentiality" | "Integrity" | "Availability",
    "reasoning": "<how it was considered an asset, grounded in the RTL>",
    "related structural assets": [
      {"asset rtl": "<exact declared name from the closed set; a field of an internal record signal is written with its dot, as declared. Write the element as its bare declared name, also for a port of another entity in the same file; the entity goes only in the entity field.>",
       "entity": "<the entity that declares the element, copied verbatim>",
       "realization": "stores" | "sets" | "computes" | "exit port"}

 ]}

  Established: the RTL explicitly or logically establishes that the value, state, or decision has a confidentiality, integrity, or availability property that matters to a module operation or flow.
  Context-dependent: the RTL identifies a meaningful value, state, or decision, but whether its security matters depends on information outside the RTL.
  Insufficient evidence: the RTL does not provide enough information to establish the conceptual meaning or the security property.
- Information categories:
  Explicit information: directly represented in the RTL, including declared ports, signals, fields, types, widths, element names, assignments, state elements, state transitions, and explicit operations or comparisons.
  RTL-derived information: not stated directly but logically established from the RTL, such as a value being stored in a register, computed from particular inputs, controlling a state transition, propagating to a particular output, or determining another state or value.
  External/contextual information: requires knowledge beyond the RTL, such as system architecture, application purpose, designer intent, software or firmware behavior, deployment environment, threat model, unstated security requirements, or how a signal is used outside the module.

Identify conceptual assets first, from the use-case flows; identify their structural references second. Never start by labeling individual signals as assets. Report a conceptual asset only when its evidence level is Established.

Define a concept by the meaning of the data, configuration, state, decision, or event. A signal name or the collection of everything influencing another asset is not a sufficient conceptual definition.

When mapping structural references:
- Apply the transport and sub-block connection rules.
- Distinguish value establishment from an unchanged assignment.
- Do not relabel an internal carrier as “sets” simply because it has a driver.
- Distinguish a decision from the data path it gates.
- Treat testing of a sub-block connection field as eligibility under the exception, not automatic evidence of an Established concept.
- Allow a declared element to realize distinct conceptual assets where its behavior supports them.

6. Security relevance

For each flow-derived conceptual candidate, identify the specific RTL-grounded property that must hold, and evaluate:

- Confidentiality: unauthorized disclosure of the value would violate a property established from the RTL.
- Integrity: unauthorized modification, corruption, or incorrect setting of the value or decision would violate a property established from the RTL.
- Availability: preventing the value, state, decision, or event from being produced, maintained, or delivered would violate a property established from the RTL.

Connect the candidate to the property through actual RTL behavior. Possible evidence includes release restrictions, access decisions, implemented computations, configuration-dependent behavior, state consistency, validity relationships, completion conditions, result delivery, and required retention or production. None of these patterns automatically establishes an asset.

Distinguish:
- Explicit relevance: a restriction, decision, or required relationship is directly represented in the RTL.
- RTL-derived relevance: the candidate's role and the consequence of disclosure, modification, or withholding follow logically from identified relationships.
- Context-dependent relevance: the security property requires an unavailable fact outside the RTL.

A dedicated protection mechanism or security-themed name is not required. Integrity or Availability can be Established for an ordinary operation if its dependence on a meaningful value, state, result, or event and the particular property at stake are demonstrated by the RTL.

Do not classify merely because an element has fan-out, is stored, changes behavior, or belongs to a control cone. Identify the meaningful property of the demonstrated flow. Avoid generic assumptions such as “all configuration is sensitive” or “all control signals are security-critical.”

For Confidentiality, establish a disclosure property from the RTL; do not infer secrecy from a name, storage, or encoding alone. For Availability, respect the flow's conditions and do not infer unconditional progress from unspecified external readiness or activity.

Establish why a property matters without claiming the implementation successfully protects it. Do not infer attacker capabilities or exploitability.

When the same concept has several Established objectives, keep one conceptual entry. Select Confidentiality, then Integrity, then Availability among its Established objectives for the scalar “security objective” field. This is a formatting tie-break, not a severity ranking. Explain the other Established objectives and their support in “reasoning”; do not duplicate the concept merely to fit objectives.

7. Evidence sufficiency

Support every classification with RTL evidence. Evidence is an explicit RTL fact or a conclusion that follows logically from identified RTL relationships; inference is an interpretation the RTL does not establish.

A sufficient chain for an Established conceptual asset connects: RTL evidence, then an identifiable value, state, or decision, then its security significance, then its confidentiality, integrity, or availability objective.

Element names may support interpretation but must be corroborated by RTL behavior when security relevance is not explicit. Resolve conflicting evidence conservatively. Incomplete evidence leads to Context-dependent or Insufficient evidence, never speculative completion.

Check each conceptual candidate for:
- Identifiable meaning.
- Demonstrated relationship to an implemented flow.
- A particular RTL-supported confidentiality, integrity, or availability property.
- A traceable consequence for that flow if the property fails.
- Scope limited to supported entities, behavior, and conditions.

For each structural reference, additionally establish its declaration, declaring entity, relationship to the concept, realization role, and compliance with exclusions.

Ground evidence summaries in actual assignments, comparisons, state updates, and use relationships. Names alone or unsupported labels such as “security-critical” are insufficient.

Inspect alternative paths, overwrites, initialization, competing drivers, and other uses that could contradict a claim. Narrow the claim to justified conditions where possible. Otherwise use Context-dependent or Insufficient evidence according to the missing link.

Do not mistake missing enforcement for missing relevance, and do not assert an enforcement guarantee contradicted by the RTL.

Evaluate conceptual evidence separately from structural eligibility. Do not invent structural declarations to complete a conceptual entry.

8. Uncertainty

Use the evidence levels Established, Context-dependent, and Insufficient evidence, with exactly those names.

Never resolve uncertainty by assuming common hardware-security conventions. Only Established conceptual assets and their structural references appear in the output. Decide Context-dependent and Insufficient evidence cases during analysis and do not report them.

Not established is not the same as not present: failing to establish relevance is not evidence that an element is irrelevant.

Do not add uncertainty fields, rejected-candidate lists, intermediate worksheets, or contextual speculation to the final object.

9. Analysis procedure

Run the stages in this order:
build the closed set; derive relationships; derive use-case flows; identify conceptual assets; identify their structural references; validate.

Start from the empty output object:
{"module name": "", "conceptual assets": []}

When identifying conceptual assets, fill in "module name" and add one entry per Established conceptual asset, with "related structural assets" left empty. When moving on to structural references, fill in each "related structural assets" list. Then validate the object. This filling happens during analysis; the response contains only the final, completed object.

Stage: build the closed set
- Purpose: define the only eligible structural candidates.
- Input: supplied RTL.
- Operation: inventory declarations across all supplied entities.
- Output: exact candidate names, declaration ownership, and declaration evidence.

Stage: derive relationships
- Purpose: establish behavior before classification.
- Input: RTL and the closed set.
- Operation: perform the analyses specified in Observation.
- Output: relationships distinguishing realization, local consumption, propagation, gating, transport, and entity crossings.

Stage: derive use-case flows
- Purpose: identify operations that give candidate values their meaning.
- Input: derived relationships.
- Operation: assemble coherent operations, their conditions, behavior, and results.
- Output: an RTL-grounded flow inventory with explicit boundaries.

Stage: identify conceptual assets
- Purpose: establish security-relevant meanings before selecting structures.
- Input: flows and supporting evidence.
- Operation: identify concepts, evaluate objectives and evidence levels, consolidate synonymous concepts, and add only Established concepts to the working object.
- Output: conceptual entries with grounded reasoning and empty structural lists.

Determine “module name” from the supplied RTL. Use an unambiguously identified top entity when available. Otherwise use the unique entity not instantiated by another supplied entity. If no unique root is identifiable, use the first root in source order, or the first declared entity if no root is identifiable, solely as a deterministic reporting label. Do not treat this fallback as evidence of architecture or as grounds to exclude other supplied entities from the closed set or analysis.

Stage: identify structural references
- Purpose: locate eligible realizations of Established concepts.
- Input: conceptual entries, closed set, and derived relationships.
- Operation: trace each concept to storage, setting, computation, and eligible exit points; apply all special rules and exclusions.
- Output: populated structural-reference lists.

Assign realization labels according to the RTL:
- “stores”: the element retains the conceptual value or state.
- “sets”: the element establishes the value without merely carrying it, including a locally consumed input or the permitted whole-transaction-port case.
- “computes”: the element holds a value or decision computed here.
- “exit port”: the value leaves through the declaring entity's output-capable port, subject to the transport exclusion.

For an eligible output port, represent its exit role with “exit port.” For an internal retained value, use “stores.” Otherwise distinguish computation from setting using its actual behavior. Do not duplicate a reference merely to redescribe the same realization.

If an Established concept has no eligible reference in the closed set, leave its structural list empty and concisely explain why no eligible declared reference exists. Do not fabricate an element, promote a carrier, or demote an Established concept solely because its structural list is empty.

Stage: validate
- Purpose: ensure all reported concepts and structural references satisfy the methodology.
- Input: working object, RTL, inventory, and relationships.
- Operation: apply Validation and correct unsupported or inconsistent entries.
- Output: the final schema-compliant object.

If later evidence contradicts an earlier conclusion, correct the conclusion without bypassing conceptual-before-structural analysis.

10. Validation

Before responding, validate each concept:
- Its meaning is identifiable in the RTL.
- Its flow was established from RTL behavior.
- Its evidence level is Established.
- Its selected security objective has a specific supported property and consequence.
- Its reasoning contains no dependence on comments, external assumptions, names alone, or invented environmental behavior.
- Necessary conditions and boundaries are respected.
- Asset relevance is not confused with successful enforcement, vulnerability, or exploitability.

Validate each structural reference:
- “asset rtl” is an exact name from the closed set.
- “entity” is the declaring entity's name, copied verbatim.
- The element name is bare, without an entity prefix, instance hierarchy, invented alias, or synthetic expression.
- An internal record field is written using its declared record-signal name and declared field path with dots, not an entity qualification.
- No field of a port is reported.
- Its realization label is supported for the associated concept.
- A locally consumed input is distinguished from an input merely forwarded elsewhere.
- Clock, clock-enable, and reset inputs obey their stated exception.
- No carrier is reported.
- No transport payload is reported, whole or by field.
- A transaction port appears only for an access-control decision taken directly on one of its security attributes, with no internal element holding the decision.
- Passing a security attribute unchanged is not treated as making a decision.
- A sub-block connection field meets the local-test or local-computation exception and independently qualifies as a realization.
- Mere influence on an asset is not mistaken for realization.

Remove redundant parent-record and field references that merely redescribe the same realization. Preserve distinct supported references and conceptual meanings.

If bare names collide across declaration scopes, do not invent qualified names in “asset rtl.” Use declaration ownership and concise reasoning to preserve the relevant distinction.

Check the final object:
- Every supplied entity was considered when building the closed set.
- Aliases and scalar-objective formatting have not created duplicate conceptual entries.
- No unsupported structural additions remain.
- Only prescribed keys and enum values appear.
- The output is the final JSON object, with no intermediate analysis.
- If the conceptual list is empty, this means no conceptual asset was Established, not that the design has no security concerns.
