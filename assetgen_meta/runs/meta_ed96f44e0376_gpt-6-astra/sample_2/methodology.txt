1. Information

The executor distinguishes the three information categories defined below. Only explicit and RTL-derived information may be used to classify an asset. External/contextual information is never silently converted into an RTL fact. If the security relevance of an element depends on unavailable external information, that dependency is treated as Context-dependent, not assumed. The analysis answers, in order: what is explicitly present in the RTL; what can be logically established from it; what remains unknown because it needs external context.

The execution input is only the RTL of one hardware IP module, with all comments removed. The RTL may declare more than one entity. The RTL is the sole authoritative source for the analysis. Comments are not a source of evidence. Names, conventional interfaces, and familiar implementation patterns do not authorize assumptions about undocumented intent or deployment.

The executor maintains an internal evidence record separating:
- Explicit observations and their locations in declarations or executable RTL.
- Relationships logically derived using the RTL language’s semantics.
- Unresolved questions and the external information needed to answer them.

The response contains concise, RTL-grounded justifications, not private chain-of-thought or the executor’s internal working record.

2. Observation

The executor first builds the closed set, recording for each element its exact declared name and the entity that declares it. Expressions, assignments, operators, processes, functions, procedures, state transitions, conditions, and similar constructs are not assets; they are evidence about declared elements. The executor derives relationships from the RTL before classifying anything, and distinguishes a value’s origin or realization point from the intermediate elements it later travels through.

Build a declaration inventory covering every entity in the supplied RTL. Record each candidate’s declared name, declaring entity, kind, direction where applicable, type, width where resolvable, and identifiable internal record fields. Preserve names verbatim. A field of an internal record signal is represented relative to that signal using its dot notation, not an instance hierarchy prefix. Port fields are not separate candidates.

Derive relationships using:
- Data-flow analysis: drivers, reads, assignments, operand dependencies, transformations, selectors, field updates, and connections to ports.
- Control-flow analysis: conditions, branch priority, case alternatives, conditional assignments, enable conditions, and which updates or outputs each condition controls.
- State analysis: retained values, reset or initialization behavior, update conditions, state transitions, and the distinction between combinational computation and storage.
- Structural analysis: entity boundaries, instantiations, port mappings, record connections, and the distinction between behavior implemented in this entity and behavior implemented elsewhere.
- Dependency analysis: distinguish data dependencies from control dependencies, and distinguish local realization from forwarding or gating.
- Behavioral analysis: explicit comparisons, arithmetic or logical relations, selection rules, access decisions, event generation, and locally established input-to-output or state-to-output properties.

Interpret assignments and processes under the applicable RTL semantics, including priority, partial assignments, and multiple drivers. Do not infer a definite value or property where those semantics or missing declarations leave it unresolved.

Functions and procedures may be inspected to derive the behavior of their callers when their bodies are supplied. An unavailable implementation is opaque. Expressions or function calls never become additional candidates.

Annotate relationships that may later invoke special rules: complete-transaction record transport, transaction security attributes, sub-block connection fields, ordinary clock or reset infrastructure, and outward ports. These annotations describe behavior; they do not yet classify assets.

The stage produces a relationship model connecting declared candidates to identifiable values, decisions, states, computations, storage points, uses, and outputs. Connectivity alone does not establish either conceptual meaning or primary status.

3. Use-case flows

Before identifying conceptual assets, the executor derives the module’s use-case flows from the RTL alone.

Recognize flows by tracing coherent behavior from an initiating input, an accepted condition, a state predicate, or continuously evaluated operands through operations and state changes to an observable effect, retained state, computed result, decision, or event. Both combinational behavior and sequential behavior can implement a flow.

Describe each flow using:
- A behavioral name grounded in what the RTL does.
- The declaring entities and available implementation boundaries involved.
- Its initiating or enabling conditions.
- The values consumed and the operations or decisions performed.
- State updates, result formation, status or event production, and outward effects.
- The RTL relationships establishing these steps.
- Any locally established correctness, access, preservation, or progress property.
- Any unresolved dependency on external behavior.

Do not require a software-driven lifecycle, a particular protocol, or a security-oriented purpose. Derive configuration, operation, reporting, and readout flows only where the RTL implements them. Merge behavior into a flow when its causal relationship is established; do not join disconnected behavior merely because names suggest a common purpose.

These flow descriptions are the input to conceptual asset identification, not an asset list.

4. External information

Conclusions requiring external/contextual information include undocumented data sensitivity, authorization policy, system privilege assignments, intended users, firmware sequencing, protection provided elsewhere, external timing guarantees, the meaning of an opaque sub-block, and the use of an output after it leaves the supplied RTL.

For each such dependency, record internally:
- What the RTL establishes.
- What proposed conclusion would require additional information.
- What information is missing.
- Whether that gap prevents establishing conceptual meaning or only security relevance.

When a meaningful value is identifiable but its security relevance depends on the missing information, use Context-dependent. When the RTL does not establish the value’s meaning or the property being asserted, use Insufficient evidence. Do not invent missing declarations, policies, contracts, or behavior.

Use standard RTL language semantics to interpret the source, but do not treat familiarity with a design pattern as evidence of system intent. An unresolved type, parameter, imported definition, or instantiated implementation limits the conclusions that depend on it; it does not invalidate unrelated, established relationships.

Missing context does not prove that an asset is absent or irrelevant. It limits what may be reported from this input.

5. Asset definition

Apply the following definitions.

- Two axes. Assets are classified along two independent axes: abstraction (conceptual vs structural, from IEEE P3164) and dependency (primary vs secondary, from SAIF).
- Conceptual asset: a piece of data, configuration, or system state (including a decision or event the module computes) that a use-case flow of the IP depends on, and whose confidentiality, integrity, or availability must hold for that flow to be secure. It is defined by what it means, not where it is. It must be identifiable from the RTL as a value the module produces, stores, or uses.
- Structural asset (structural reference): a declared RTL element (a port, a signal, or a field of an internal record signal) that realizes a conceptual asset: where its value is stored, set, or computed, or the port through which it leaves its entity. An element that only passes the value along, or gates it on the way, carries the asset but is not its structural reference. An input port whose value this entity itself reads, to store it, compute from it, or decide on it, is where that value enters the entity: it is a structural reference of the concept it carries, with realization "sets". Clock, clock-enable and reset inputs are not structural references in this way, unless controlling a clock or a reset is this block's function, in which case they are (clock and reset are security concerns: CWE-1206). A port whose record type carries complete bus transactions is governed by the Transport definition instead. One conceptual asset usually has several structural references along its path, and one element can realize several conceptual assets.
- Primary asset: a primary asset is an element that stores, sets, or computes a security-relevant value or decision, or a port through which such a value leaves its entity. Elements that only pass the value along or gate it between those points are not primary, but secondary assets. An input port whose value this entity itself reads, to store it, compute from it, or decide on it, is where that value is set. At module level, the primary assets are the structural references of the conceptual assets. These are what the executor reports.
- Secondary asset: an element that only passes a primary asset's value along or gates it between those points, or an internal signal or register that influences a primary asset or could violate its security objective. The executor never reports secondary assets; a later stage finds them from connectivity.
- Transport: a port or signal whose record type carries complete read or write transactions between this block and an interconnect is transport for its payload: the address, write data, byte enables, strobe, acknowledge and read data. The payload is not a primary asset: do not report it, whole or by field. Do not use a transport element as the exit of a value that a register holds and software can read back, or as the element that sets a value written into this block; report the element inside the block that stores or decides the value. A security attribute carried with a transaction is different: a privilege level, a debug-mode flag, or a source or initiator identifier (the concern of CWE-1302, CWE-1311, CWE-1317 and CWE-1318). When this block decides on such an attribute, for example to allow, deny, bypass or route an access, that access-control decision is a conceptual asset. Its structural reference is the internal element that computes or stores the decision; if the decision is taken directly on the attribute, with no internal element holding it, the structural reference is the transaction port, named whole. An attribute that is only passed along unchanged is carried, not decided. A port is a single candidate: name it whole; never report a field of a port.
- Sub-block connection field: a field of an internal record that only connects this block to an instantiated sub-block, receiving one of its outputs or passing a value unchanged to one of its inputs, is a carrier. Do not report it unless this block tests it in an if, case or when condition, or computes it here from a decision.
- Use-case flow: an operation the RTL implements, such as configuring the module, starting an operation, computing a result, reporting status, or reading out data.
- Closed set (candidate universe): the declared ports of every entity in the RTL, the declared internal signals, and the individually identifiable fields of internal record signals. A port is a single candidate; its fields are not candidates. Nothing else can be a structural asset.
- Evidence levels:
  Established: the RTL explicitly or logically establishes that the value, state, or decision has a confidentiality, integrity, or availability property that matters to a module operation or flow.
  Context-dependent: the RTL identifies a meaningful value, state, or decision, but whether its security matters depends on information outside the RTL.
  Insufficient evidence: the RTL does not provide enough information to establish the conceptual meaning or the security property.
- Information categories:
  Explicit information: directly represented in the RTL, including declared ports, signals, fields, types, widths, element names, assignments, state elements, state transitions, and explicit operations or comparisons.
  RTL-derived information: not stated directly but logically established from the RTL, such as a value being stored in a register, computed from particular inputs, controlling a state transition, propagating to a particular output, or determining another state or value.
  External/contextual information: requires knowledge beyond the RTL, such as system architecture, application purpose, designer intent, software or firmware behavior, deployment environment, threat model, unstated security requirements, or how a signal is used outside the module.

Conceptual assets are identified first, from the use-case flows; their structural references are identified second. The analysis never starts by labeling individual signals as assets. A conceptual asset is reported only when its evidence level is Established.

Identify a concept by its semantic role in a flow, not by a declaration name or physical location. Reuse the same concept across flows when the RTL establishes that they depend on the same meaningful value, state, decision, or event. Do not merge different meanings merely because they share storage or connectivity.

6. Security relevance

For each proposed concept, identify a specific property established by the RTL, its relevance to a derived use-case flow, and what would be violated by disclosure, incorrect value or decision, or suppression. Security relevance is tied to one or more of:
- Confidentiality: unauthorized disclosure of the value would violate a property established from the RTL.
- Integrity: unauthorized modification, corruption, or incorrect setting of the value or decision would violate a property established from the RTL.
- Availability: preventing the value, state, decision, or event from being produced, maintained, or delivered would violate a property established from the RTL.

Apply these tests:
- Confidentiality requires evidence of a value-specific disclosure restriction or other RTL-established property that disclosure would violate. A suggestive name, inaccessible-looking storage, or an assumed application does not establish confidentiality.
- Integrity requires a concrete value, state, result, or decision whose correct setting or preservation matters to an implemented flow. Identify the relevant update rule, result relation, decision rule, or state invariant and the flow consequence of violating it.
- Availability requires an identifiable production, preservation, completion, or delivery role established by the RTL. State the local event or behavior that suppression would prevent. Do not infer an external service guarantee or unconditional liveness from an implementation that depends on unestablished environmental behavior.

A concrete RTL-implemented correctness or progress property can establish Integrity or Availability; dedicated security circuitry is not required. However, “changing this wire could change an output” is not a sufficient justification. The analysis must identify the meaningful concept and the specific flow property at issue.

Distinguish:
- Explicit relevance: the RTL directly represents the relevant restriction, decision, preservation rule, or required operation.
- RTL-derived relevance: the property and its consequence follow from identified data-flow, control-flow, or state relationships.
- Context-dependent relevance: the proposed security significance requires an unstated purpose, policy, sensitivity classification, or environmental guarantee.

Avoid generic assumptions such as “all configuration is sensitive” or “all control signals are security-critical.” Do not promote an influencing signal to primary status simply because corrupting it could affect an established asset.

Do not require or invent an attacker, exploit path, vulnerability, or likelihood estimate. Asset identification is separate from vulnerability discovery, exploitability analysis, and threat assessment; consider a contextual dependency only when it is needed to define relevance.

7. Evidence sufficiency

Every classification is supported by evidence from the RTL. Evidence is an explicit RTL fact or a conclusion that follows logically from identified RTL relationships; inference is an interpretation the RTL does not establish. A sufficient chain for an Established conceptual asset connects: RTL evidence, then an identifiable value, state, or decision, then its security significance, then its confidentiality, integrity, or availability objective. Element names may support interpretation but are corroborated by RTL behavior when security relevance is not explicit. Conflicting evidence is resolved conservatively; incomplete evidence leads to Context-dependent or Insufficient evidence, never to speculative completion.

For each proposed concept, maintain a compact internal evidence record identifying:
- The relevant declarations, assignments, comparisons, operations, or state behavior.
- The meaningful value, state, decision, or event established by those facts.
- The use-case flow that produces, stores, or uses it.
- The specific property that would be violated.
- The supported security objective.
- Any premise not established by the RTL.

A logical derivation must remain valid under the relevant branches, priorities, drivers, and state-update semantics. Do not infer protection from one branch while ignoring another branch that bypasses it. Do not treat apparent reachability, constant propagation, or mutual exclusion as established unless it follows from the available RTL.

Distinguish evidence from inference by asking whether the conclusion follows without assigning an undocumented purpose to the element or adding an environmental premise. If it does not, record the premise as missing rather than hiding it in the justification.

When evidence conflicts, first check whether the observations describe different conditions or phases. If the RTL resolves the difference, qualify the conclusion accordingly. If it does not, do not select the preferred interpretation. Classify the unsupported claim as Context-dependent or Insufficient evidence, while retaining independently established conclusions.

An Established classification does not claim that the design enforces the objective perfectly. Conversely, an apparent design defect does not by itself identify a conceptual asset. Report the established value and objective, not a vulnerability assessment.

8. Uncertainty

The executor uses the three evidence levels defined above, with exactly those names: Established, Context-dependent, and Insufficient evidence. Uncertainty is never resolved by assuming common hardware-security conventions. Only Established conceptual assets, and their structural references, appear in the output. Context-dependent and Insufficient evidence cases are decided during the analysis and are not reported. Not established is not the same as not present: failing to establish relevance is not evidence that an element is irrelevant.

Uncertainty concerning one value, field, flow, or implementation boundary is not automatically transferred to unrelated conclusions. Report only claims whose own evidence is sufficient.

9. Analysis procedure

The stages run in this order: build the closed set; derive relationships; derive use-case flows; identify conceptual assets; identify their structural references; validate.

The executor starts from the empty output object:
{"module name": "", "conceptual assets": []}

When it identifies conceptual assets, it fills in "module name" and adds one entry per Established conceptual asset, with "related structural assets" left empty. When it moves on to structural references, it fills in each "related structural assets" list. It then validates the object. This filling happens during the analysis; the response contains only the final, completed object.

Stage: build the closed set.
- Purpose: establish the exhaustive candidate universe without classifying assets.
- Input: the supplied RTL.
- Operation: inventory declarations and ownership as specified in Observation.
- Output: the closed set and declaration metadata.

Stage: derive relationships.
- Purpose: distinguish local realization from influence, transport, and forwarding.
- Input: the closed set and executable RTL.
- Operation: perform the analyses in Observation, respecting entity boundaries and available implementations.
- Output: the RTL-derived relationship model and explicit unresolved dependencies.

Stage: derive use-case flows.
- Purpose: establish the implemented operations that give values semantic meaning.
- Input: declarations and the relationship model.
- Operation: trace and describe flows as specified in Use-case flows.
- Output: grounded flow descriptions with their local properties and information gaps.

Stage: identify conceptual assets.
- Purpose: identify meaningful values and supported security objectives before mapping them to elements.
- Input: the flow descriptions, relationship model, and evidence records.
- Operation: apply the definitions, security-relevance tests, and evidence-sufficiency rules. Classify each proposed concept as Established, Context-dependent, or Insufficient evidence. Consolidate references to the same concept without merging distinct meanings.
- Output: fill the module name and create entries only for Established concepts, leaving structural-reference lists empty.

Determine "module name" from the supplied declarations. Use the sole declared entity when applicable. Otherwise, use the unique entity not instantiated by another supplied entity when that root is identifiable. If there are multiple such roots, use the first declared root; if no root is identifiable, use the first declared entity. The fallback is only a deterministic label for the analysis, not a claim about deployment or system hierarchy. It does not restrict the closed set or exclude other supplied entities from analysis. Fill this name even if no concept is Established.

For each concept, the schema’s "security objective" contains the objective most directly supported by its cited RTL property. If other objectives are also Established, they may be mentioned concisely in "reasoning"; do not invent a combined enumeration value or duplicate the concept solely to encode those objectives.

Stage: identify structural references.
- Purpose: identify the primary elements that realize each Established concept.
- Input: Established conceptual entries, the closed set, and the relationship model.
- Operation: trace each concept to its actual setting, storage, computation, and outward interface points, applying all exclusions and special cases in the definitions.
- Output: fill each "related structural assets" list with supported structural references.

Apply the following structural decisions:
- Use "stores" for an element retaining the concept as state.
- Use "sets" for an input that its declaring entity itself consumes to store, compute from, or decide on the carried value, and for another genuine setting point established by the RTL rather than a forwarding point.
- Use "computes" for an element realizing a locally derived value, decision, or event.
- Use "exit port" for a port through which the established value leaves its declaring entity, subject to the transport exclusion.
- If an element supports different roles, use a realization supported by its relationship to this concept. Do not label an alias or gate as a setting or computation point merely because it has an assignment.
- Exclude elements that only carry or gate an existing concept. A computed decision controlling a gate can be a different conceptual asset if its meaning and security relevance are independently Established.
- Exclude ordinary clock, clock-enable, and reset inputs under the specified exception rule.
- Recognize transport from the record type and implemented complete-transaction behavior, not merely an interface name. Do not suppress unrelated non-transport ports merely because they resemble bus signals.
- For transport payloads, report the internal storage or decision element instead of the transport element. For security attributes, distinguish deciding from unchanged forwarding and apply the exact transaction-port fallback in the Transport definition.
- For sub-block connection fields, enforce the stated test-or-compute exception. Meeting that exception permits further consideration; it does not establish conceptual meaning or security relevance by itself.
- Analyze each supplied entity’s ports in the context of the entity that declares them. A parent’s forwarding connection is not automatically a realization of a concept computed by a child.

Stage: validate.
- Purpose: remove unsupported classifications and representation errors.
- Input: the completed draft object and all supporting RTL relationships.
- Operation: apply Validation, revisiting earlier conclusions if a contradiction is found.
- Output: the final JSON object only.

10. Validation

Audit each conceptual entry for:
- An identifiable value, state, decision, or event produced, stored, or used by the RTL.
- A derived use-case flow that depends on it.
- A specific, RTL-established security property supporting the selected objective.
- A sufficient evidence chain with no hidden external premise.
- A semantic identity distinct from other entries, unless the entries describe genuinely different concepts.
- A concise "reasoning" statement explaining the flow, concrete RTL behavior, and objective without exposing private chain-of-thought.

Audit each structural reference for:
- Exact membership in the closed set.
- An "asset rtl" value that is the bare declared name. Internal record fields use their dot notation; do not add entity names, instance paths, or undeclared expression text.
- An "entity" value copied verbatim from the entity that declares the element, including for ports of other entities in the same input.
- A direct realization of the associated concept, with the selected realization supported by the RTL.
- No carrier incorrectly promoted to primary status.
- No transport payload, either whole or by field.
- No field of a port.
- A transaction port only when it is the structural reference of an access-control decision taken directly on one of its security attributes, with no internal element holding the decision.
- Compliance with the clock/reset exception and the sub-block connection field rule.

Check coverage by revisiting the established concept’s setting, storage, computation, and outward interface relationships; do not stop at the first convenient name. Conversely, do not add fan-in, fan-out, aliases, or gating elements merely to expand coverage. Recheck any concept whose structural mapping cannot be supported without inventing a candidate.

Check that branch conditions, drivers, entity boundaries, and missing implementation details do not contradict the stated reasoning. Downgrade and omit concepts whose relevance is not Established. Remove unsupported structural references without automatically discarding an independently Established concept.

Check that the final object has exactly the required keys and allowed enumeration values, valid JSON quoting and escaping, the selected module name, and no analysis-only evidence-level fields or secondary-asset lists.

11. Output representation

The executor returns the EXECUTOR OUTPUT SCHEMA below and nothing else.

Return ONE JSON object and nothing else: no markdown, no code fences, no prose. Use the keys exactly as written.
{"module name": "<the module analysed>",
 "conceptual assets": [
   {"concept": "<the conceptual asset identified>",
    "security objective": "Confidentiality" | "Integrity" | "Availability",
    "reasoning": "<how it was considered an asset, grounded in the RTL>",
    "related structural assets": [
      {"asset rtl": "<exact declared name from the closed set; a field of an internal record signal is written with its dot, as declared. Write the element as its bare declared name, also for a port of another entity in the same file; the entity goes only in the entity field.>",
       "entity": "<the entity that declares the element, copied verbatim>",
       "realization": "stores" | "sets" | "computes" | "exit port"}
    ]}
 ]}
If the module has no Established conceptual assets, return {"module name": "<the module analysed>", "conceptual assets": []}.
