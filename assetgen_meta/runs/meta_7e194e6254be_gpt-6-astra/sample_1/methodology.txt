1. Information

The executor receives only the RTL of one hardware IP module, with all comments removed. The RTL may declare more than one entity. The RTL is the sole authoritative source. Comments are not an evidence source.

The executor distinguishes the three information categories defined below. Only explicit and RTL-derived information may be used to classify an asset. External/contextual information is never silently converted into an RTL fact. If the security relevance of an element depends on unavailable external information, that dependency is treated as Context-dependent, not assumed. The analysis answers, in order: what is explicitly present in the RTL; what can be logically established from it; what remains unknown because it needs external context.

Maintain an internal evidence record that separates declarations and operations actually present, relationships logically established from them, and unresolved contextual dependencies. Classification must depend on the first two categories, not on the plausibility of an interpretation.

This is asset identification, not vulnerability discovery, exploitability analysis, or threat assessment. Discuss a dependency on an external security requirement only to determine whether asset relevance is established.

2. Observation

First build the closed set, recording each candidate’s exact declared name and declaring entity. Expressions, assignments, operators, processes, functions, procedures, state transitions, conditions, and similar constructs are not assets; they are evidence about declared elements. Derive relationships before classifying anything. Distinguish a value’s origin or realization point from intermediate elements it later travels through.

For each candidate, record applicable observable properties:
- Declaration kind, direction, type, width, signedness, and record structure.
- Declaring entity and declaration scope.
- Drivers, readers, assignment conditions, and in-file instance connections.
- Whether assignments retain state, create a local value, compute a decision, forward a value, or gate its propagation.
- Whether the candidate is a complete-transaction record, a sub-block connection field, or an input subject to the clock, clock-enable, or reset exception.

Construct relationships using:
- Def-use and assignment analysis, including conditional assignments and record-field assignments.
- Combinational data-flow analysis, preserving operation semantics, bit widths, selection, and signedness.
- Control-dependence analysis of conditions, comparisons, branch decisions, and state transitions.
- Sequential analysis of capture, update, hold, initialization, reset, and release behavior.
- Connectivity analysis across entities whose declarations and implementations are present.
- Backward tracing from produced values and decisions, and forward tracing from consumed inputs and stored state.

Do not equate syntactic computation with conceptual computation. Copying, repackaging, selecting, or masking can merely transport or gate an existing value. A selector or predicate may independently realize a decision, while the selected data path remains a carrier of a different concept.

Do not invent declarations, instance internals, record fields, timing guarantees, or protocol semantics. Unresolved types, missing bodies, and unsupported constructs remain explicit analysis gaps.

The result is a relationship model connecting declared elements to values, computations, decisions, state updates, conditions, and entity outputs. It does not yet label elements as assets.

Determine the analysis identifier from declarations and the in-file instantiation graph. Use an unambiguous declared IP root name when the RTL establishes one. Otherwise, use a composite identifier formed from the exact candidate-root names, sorted lexicographically and joined with “ | ”. If roots cannot be established, use the exact declared entity names in that form. This is an input-scope identifier, not an assertion of an unstated top-level architecture. Regardless of the identifier, examine the declared entities throughout the supplied RTL.

3. Use-case flows

Derive use-case flows from the relationship model before identifying conceptual assets.

Recognize flows through connected RTL behavior: input consumption, state capture or configuration, conditional initiation, computation, state progression, status generation, completion, and output or readout. These are recognition patterns, not requirements that every design implement them.

Describe each flow internally by:
- The operation the RTL performs, using a behavior-grounded description.
- Its entry event or enabling condition, where identifiable.
- Values and existing state it consumes.
- Decisions and state updates it performs.
- Values, events, or states it produces.
- Its observable result, exit, completion condition, or continuing behavior.
- Guards, reset conditions, alternative paths, and unresolved dependencies relevant to those relationships.

Flows may overlap or share state. Do not assume external actors, software sequences, protocol obligations, algorithmic purpose, or eventual progress not established by the RTL. For an external interaction, describe only the local behavior and conditions actually implemented.

The flow descriptions supply the semantic context for identifying conceptual values; they are not structural-asset lists.

4. External information

External information is required for conclusions about unstated authorization, intended secrecy, deployment-specific sensitivity, external consumers, application purpose, software discipline, environmental fairness, attacker capabilities, or system-wide security guarantees.

Names, interfaces, arithmetic patterns, and recognizable implementation idioms may suggest these interpretations, but do not establish them without corroborating RTL behavior. A declaration of an unavailable component or package does not establish its implementation.

For each material gap:
- Identify the proposition the RTL establishes.
- Identify the additional proposition needed for the security conclusion.
- Determine whether that additional proposition follows from the supplied RTL.
- If it does not, leave it unknown rather than supplying conventional assumptions.

A meaningful value whose security significance requires the missing proposition is Context-dependent. If even the conceptual meaning or relevant property cannot be established adequately, use Insufficient evidence.

An externally uncertain property does not invalidate a different property independently established from the RTL. Limit every established conclusion to its supported scope and conditions.

5. Asset definition

Apply the following definitions. Conceptual assets are identified first, from the use-case flows; their structural references are identified second. The analysis never starts by labeling individual signals as assets. A conceptual asset is reported only when its evidence level is Established.

DEFINITIONS

- Two axes. Assets are classified along two independent axes: abstraction (conceptual vs structural, from IEEE P3164) and dependency (primary vs secondary, from SAIF).
- Conceptual asset: a piece of data, configuration, or system state (including a decision or event the module computes) that a use-case flow of the IP depends on, and whose confidentiality, integrity, or availability must hold for that flow to be secure. It is defined by what it means, not where it is. It must be identifiable from the RTL as a value the module produces, stores, or uses.
- Structural asset (structural reference): a declared RTL element (a port, a signal, or a field of an internal record signal) that realizes a conceptual asset: where its value is stored, set, or computed, or the port through which it leaves its entity. An element that only passes the value along, or gates it on the way, carries the asset but is not its structural reference. An input port whose value this entity itself reads, to store it, compute from it, or decide on it, is where that value enters the entity: it is a structural reference of the concept it carries, with realization "sets". Clock, clock-enable and reset inputs, and ports whose record type carries complete bus transactions, are not structural references in this way. One conceptual asset usually has several structural references along its path, and one element can realize several conceptual assets.
- Primary asset: a primary asset is an element that stores, sets, or computes a security-relevant value or decision, or a port through which such a value leaves its entity. Elements that only pass the value along or gate it between those points are not primary, but secondary assets. An input port whose value this entity itself reads, to store it, compute from it, or decide on it, is where that value is set. At module level, the primary assets are the structural references of the conceptual assets. These are what the executor reports.
- Secondary asset: an element that only passes a primary asset's value along or gates it between those points, or an internal signal or register that influences a primary asset or could violate its security objective. The executor never reports secondary assets; a later stage finds them from connectivity.
- Transport: a port or signal whose record type carries complete read or write transactions between this block and an interconnect (address, write data, byte enables, strobe, acknowledge, read data) is transport. Do not report it, whole or by field. Do not use it as the exit of a value that a register holds and software can read back, or as the element that sets a value written into this block. Report the element inside the block that stores or decides the value. A port is a single candidate: name it whole; never report a field of a port.
- Sub-block connection field: a field of an internal record that only connects this block to an instantiated sub-block, receiving one of its outputs or passing a value unchanged to one of its inputs, is a carrier. Do not report it unless this block tests it in an if, case or when condition, or computes it here from a decision.
- Use-case flow: an operation the RTL implements, such as configuring the module, starting an operation, computing a result, reporting status, or reading out data.
- Closed set (candidate universe): the declared ports of every entity in the RTL, the declared internal signals, and the individually identifiable fields of internal record signals. A port is a single candidate; its fields are not candidates. Nothing else can be a structural asset.
- Evidence levels:
  Established: the RTL explicitly or logically establishes that the value, state, or decision has a confidentiality, integrity, or availability property that matters to a module operation or flow.
  Context-dependent: the RTL identifies a meaningful value, state, or decision, but whether its security matters depends on information outside the RTL.
  Insufficient evidence: the RTL does not provide enough information to establish the conceptual meaning or the security property.
- Information categories:
  Explicit information: directly represented in the RTL, including declared ports, signals, fields, types, widths, element names, assignments, state elements, state transitions, and explicit operations or comparisons.
  RTL-derived information: not stated directly but logically established from the RTL, such as a value being stored in a register, computed from particular inputs, controlling a state transition, propagating to a particular output, or determining another state or value.
  External/contextual information: requires knowledge beyond the RTL, such as system architecture, application purpose, designer intent, software or firmware behavior, deployment environment, threat model, unstated security requirements, or how a signal is used outside the module.

6. Security relevance

For each meaningful value, state, decision, or event identified from a flow, formulate a specific property and identify how that flow depends on it.

Security relevance is tied to one or more of:
- Confidentiality: unauthorized disclosure of the value would violate a property established from the RTL.
- Integrity: unauthorized modification, corruption, or incorrect setting of the value or decision would violate a property established from the RTL.
- Availability: preventing the value, state, decision, or event from being produced, maintained, or delivered would violate a property established from the RTL.

Use an RTL-grounded property witness:
- Confidentiality requires evidence of a disclosure restriction or comparable information-release property. Being internal, having a suggestive name, or lacking a direct output is not sufficient.
- Integrity requires a specific relationship between the value or decision and the flow’s implemented acceptance, update, computation, sequencing, or reporting behavior. Identify what established relationship would be violated by incorrect setting or corruption.
- Availability requires a specific dependency on producing, retaining, or delivering the value, state, decision, or event. Identify the locally established operation that would be prevented or interrupted. Do not assume external fairness, deadlines, service guarantees, or unconditional completion.

A concrete RTL-established functional invariant may support Integrity or Availability without a dedicated security mechanism. Conversely, mere influence on another element, membership in a dependency cone, or the possibility of changing a bit does not establish a conceptual asset.

Distinguish:
- Explicit relevance: the relevant restriction, check, decision, or operational property is directly represented by RTL behavior.
- RTL-derived relevance: the property follows from identified data-flow, control-flow, or state relationships.
- Context-dependent relevance: the security conclusion needs an unstated interpretation or requirement.

Do not assume that all configuration is sensitive, all control signals are security-critical, all data is confidential, or every output has security significance. Treat unauthorized interference as the objective’s counterfactual; do not infer that an attacker or exploitable path exists.

The schema has a singular “security objective” field. If different objectives are independently established for the same concept, select the first established objective in the schema’s order—Confidentiality, Integrity, Availability—as a serialization convention, and state the other established objectives in “reasoning”. This convention does not rank their importance. Do not create different concepts solely to encode objective labels.

7. Evidence sufficiency

Every classification is supported by evidence from the RTL. Evidence is an explicit RTL fact or a conclusion that follows logically from identified RTL relationships; inference is an interpretation the RTL does not establish. A sufficient chain for an Established conceptual asset connects: RTL evidence, then an identifiable value, state, or decision, then its security significance, then its confidentiality, integrity, or availability objective. Element names may support interpretation but are corroborated by RTL behavior when security relevance is not explicit. Conflicting evidence is resolved conservatively; incomplete evidence leads to Context-dependent or Insufficient evidence, never to speculative completion.

For each proposed concept, maintain an internal evidence record containing:
- Its behavior-grounded meaning and supporting flow.
- Relevant declarations, assignments, comparisons, state updates, or output relationships.
- The specific security property and the dependency connecting it to the flow.
- Conditions under which the property holds.
- Any missing premise, counterevidence, or unresolved semantics.
- The resulting evidence level.

A sufficient derivation must preserve RTL semantics, including conditional execution, finite widths, reset behavior, alternative assignments, and entity boundaries when relevant. A property established only under a condition must not be stated unconditionally.

Resolve apparently conflicting evidence by checking whether it concerns different paths, states, conditions, or interpretations. If a contradiction cannot be resolved from the RTL, do not retain the disputed conclusion as Established. Missing evidence for a particular objective does not negate independently sufficient evidence for another.

Reasoning in the final object is a concise evidence justification, not a private chain-of-thought transcript. Cite recognizable declarations and behavior; do not invent source locations, execution traces, or verification results.

8. Uncertainty

The executor uses the three evidence levels defined above, with exactly those names. Uncertainty is never resolved by assuming common hardware-security conventions. Only Established conceptual assets, and their structural references, appear in the output. Context-dependent and Insufficient evidence cases are decided during the analysis and are not reported. Not established is not the same as not present: failing to establish relevance is not evidence that an element is irrelevant.

9. Analysis procedure

The stages run in this order: build the closed set; derive relationships; derive use-case flows; identify conceptual assets; identify their structural references; validate.

The executor starts from the empty output object:
{"module name": "", "conceptual assets": []}

When it identifies conceptual assets, it fills in "module name" and adds one entry per Established conceptual asset, with "related structural assets" left empty. When it moves on to structural references, it fills in each "related structural assets" list. It then validates the object. This filling happens during the analysis; the response contains only the final, completed object.

Stage: build the closed set.
- Purpose: establish the only permissible structural candidates.
- Input: supplied RTL.
- Operation: inventory declarations and ownership, identify record-field candidates, and record exclusions and unresolved declarations without classifying security relevance.
- Output: candidate inventory and source-grounded declaration metadata.

Stage: derive relationships.
- Purpose: establish what the RTL does and where values are realized or merely carried.
- Input: RTL and candidate inventory.
- Operation: perform the analyses in Section 2; construct in-file entity connectivity and determine the analysis identifier.
- Output: relationship model with semantic gaps recorded.

Stage: derive use-case flows.
- Purpose: recover behavior-grounded operations before proposing assets.
- Input: relationship model.
- Operation: construct the flow descriptions in Section 3.
- Output: supported flows and their data, state, decision, and output dependencies.

Stage: identify conceptual assets.
- Purpose: determine which meanings have established security relevance.
- Input: flows, relationship model, and evidence rules.
- Operation: identify meaningful values, states, decisions, and events; apply the security-property tests; assign evidence levels. Fill in the module identifier even if no concept qualifies.
- Output: entries for Established concepts, with concise reasoning and empty structural-reference lists.

Stage: identify structural references.
- Purpose: locate the primary realizations of each Established concept.
- Input: Established concepts, relationship model, and closed set.
- Operation: trace each concept to its actual storage, setting, computation, consumed-input entry, and eligible entity exits. Apply all exclusion rules before adding references.
- Output: the populated “related structural assets” lists.

Apply the following structural decisions:
- Reject anything outside the closed set.
- Exclude complete-transaction transport records and their fields. Trace transported writes and readbacks to the internal element that stores or decides the value.
- Never report a field of a port. An eligible port is named whole, even when the concept concerns only part of its value.
- Apply the stated consumed-input rule, including its clock, clock-enable, reset, and transaction-record exceptions. Pure forwarding through an input does not satisfy the consumed-input rule.
- Distinguish local value realization from intermediate carriage. A dependency on a primary asset does not itself make an element primary.
- Apply the sub-block connection-field rule. If its exception is used, identify the local if, case, or when test, or the local computation from a decision, and establish the concept and realization independently of its connection role. The exception is not a substitute for security evidence.
- An eligible outward port is an entity exit even when the output assignment forwards an existing value. This is the explicit exit-port realization, not permission to report intermediate carriers.
- A locally computed gating decision may realize its own Established concept; a data element that merely gates another concept remains secondary for that concept.
- For internal records, use the whole record only when it realizes the stated aggregate concept; use individually identifiable fields for field-specific realizations. Do not treat an entire record as an asset merely because an unrelated field matters.

Choose a supported realization label: “exit port” for an eligible outward port, “sets” for a qualifying consumed input, “stores” for retained state, “computes” for local derivation of the conceptual value or decision, or “sets” for an otherwise established setting point. When roles overlap, select the role that directly describes the reported reference; other supported roles may be explained in reasoning.

Do not invent a structural reference to fill a list. If a concept remains Established but all available realizations are excluded or outside the closed set, retain its empty list and explain the limitation concisely.

Stage: validate.
- Purpose: ensure that the completed object obeys the evidence, naming, classification, and serialization rules.
- Input: populated object and supporting analysis records.
- Operation: perform Section 10’s checks and correct unsupported entries.
- Output: the final JSON object.

10. Validation

Check the object against the supplied RTL, not against expected design intent.

For every concept:
- Confirm that its meaning is identifiable as a value the module produces, stores, or uses.
- Confirm its supporting use-case flow and complete evidence-to-objective chain.
- Confirm that its selected objective is Established, its scope is accurately qualified, and its reasoning contains no hidden external premise.
- Check relevant alternate paths, assignments, and states for contradictory evidence.
- Confirm that an apparent concept is not merely a generic label for a connectivity cone.
- Do not split or merge concepts solely because of signal naming or physical location.

For every structural reference:
- Confirm that “asset rtl” exactly matches a member of the closed set.
- Confirm that “entity” is the verbatim name of the entity that declares the candidate.
- Confirm that the name is bare: no entity or instance prefix, explanatory suffix, expression, invented slice, or synthesized identifier.
- For a field, confirm that its base is an internal record signal and that the dot-form name identifies its declared field path.
- Confirm that it is not a field of a port, a transport element, or a transport field.
- Confirm that it realizes the named concept rather than only passing, gating, influencing, or threatening it.
- Check consumed-input exceptions and any use of the sub-block connection-field exception.
- Confirm that the realization label matches the cited RTL behavior.
- Confirm that eligible entity exits are not confused with intermediate internal carriers.

Check coverage by tracing each Established concept through its eligible realization points across the supplied entities. Do not substitute a carrier for a missing source, or omit a genuine realization merely because another entity also realizes the concept.

If validation exposes a missing premise, revise the evidence level and remove unsupported reported material. If only a structural mapping is invalid, remove or correct that mapping without automatically discarding an independently Established concept.

Finally, check JSON syntax, exact keys, allowed objective and realization strings, the module identifier, and the absence of commentary or unreported evidence categories.

11. Output representation

The executor returns the EXECUTOR OUTPUT SCHEMA reproduced in the execution prompt below and nothing else.

Use one entry per Established conceptual asset, with its corresponding eligible primary structural references. The “reasoning” field gives a concise, RTL-grounded account of the flow, meaning, relevant behavior, and security objective; it does not expose private chain-of-thought.

Do not add evidence-level fields, excluded candidates, secondary assets, vulnerability findings, external-information requests, or analysis notes. If there are no Established conceptual assets, return the prescribed object with an empty “conceptual assets” list.
