1. Information

The executor distinguishes the three information categories defined below: Explicit information, RTL-derived information, and External/contextual information. Only explicit and RTL-derived information may be used to classify an asset. External/contextual information is never silently converted into an RTL fact. If the security relevance of an element depends on unavailable external information, that dependency is treated as Context-dependent, not assumed. The analysis answers, in order: what is explicitly present in the RTL; what can be logically established from it; what remains unknown because it needs external context.

The executor receives only comment-free RTL for one hardware IP module. The RTL may declare more than one entity. The RTL is the sole authoritative source. Comments are not an evidence source.

For each candidate conclusion, distinguish its supporting declarations or operations, its logically established consequences, and any missing contextual premise. Maintain concise evidence annotations during analysis; do not expose private chain-of-thought.

2. Observation

The executor first builds the closed set, recording for each element its exact declared name and the entity that declares it. Expressions, assignments, operators, processes, functions, procedures, state transitions, conditions, and similar constructs are not assets; they are evidence about declared elements. The executor derives relationships from the RTL before classifying anything, and distinguishes a value's origin or realization point from the intermediate elements it later travels through.

Build a declaration inventory covering every entity in the supplied RTL. Record direction, type, width, record structure, declaration owner, and available driving and consuming logic. Internal record fields use their declared signal-and-field path. Ports remain whole candidates, even when the RTL accesses their fields. Do not manufacture candidates from slices, array selections, expressions, instance names, or hierarchy paths.

Derive relationships using:

- Data-flow analysis: assignments, dependencies, transformations, selection, concatenation, slicing, extension, truncation, and propagation to ports.
- State analysis: storage, update and hold conditions, initialization, reset effects, counters, state encodings, and transitions.
- Control-flow analysis: conditions, comparisons, decoded choices, enables, and the values or updates they determine.
- Structural analysis: entity declarations, instantiation connections, record connections, hierarchy, and direction of value movement.
- Observability and progress analysis: which conditions expose, suppress, produce, preserve, invalidate, or deliver values and events.

Distinguish direct dependency from transitive influence, computation from unchanged forwarding, and storage from combinational propagation. A register that captures a value is a storage point even if the captured expression is an unchanged value.

Respect widths, signedness, assignment semantics, conditional elaboration, and reachable behavior when these affect a conclusion. Analyze supplied function and sub-block implementations when relevant. If an implementation, type definition, parameter value, or binding is unavailable, preserve that gap rather than assigning familiar behavior to it.

Record transport characteristics and sub-block connection patterns as structural observations. Do not yet classify elements as assets. The stage produces an evidence-linked relationship model connecting declared elements to values, decisions, states, computations, and outputs.

3. Use-case flows

Before identifying conceptual assets, the executor derives the module's use-case flows from the RTL alone.

Recognize flows from related input consumption, state updates, decisions, computations, and observable results. Include continuous operations as well as sequenced or handshake-driven operations. A flow need not correspond to a named process, and related processes may implement the same flow.

Describe each flow using:

- Its RTL-observable initiating or sustaining conditions.
- The values consumed and their established roles.
- The state, computations, and decisions involved.
- The conditions governing updates, completion, or reporting.
- Its result, status, event, or other observable effect.
- The behavioral relations the RTL establishes and any unresolved boundaries.

Use behavioral descriptions rather than assumed application purposes. Separate implemented behavior from expectations about software, users, or the surrounding system. Do not infer a transaction, access policy, or completion guarantee merely from suggestive names.

These flow descriptions provide the basis for identifying conceptual assets.

4. External information

External conclusions include application sensitivity, authorization identities not represented in the RTL, system trust boundaries, firmware protocols, deployment consequences, unstated confidentiality requirements, intended use of outputs, and unspecified behavior of external components.

Handle gaps as follows:

- Identify the missing premise and the conclusion that depends on it.
- If the RTL establishes a meaningful value or decision but security relevance requires that premise, classify that claim as Context-dependent.
- If the RTL does not establish the meaning or enough behavior to evaluate a security property, classify it as Insufficient evidence.
- Continue evaluating independent claims supported by the available RTL.

Names, protocol resemblance, cryptographic-looking operations, reset behavior, and conventional implementation patterns are not substitutes for missing premises. Do not obtain evidence from external specifications or invent missing implementations.

An unknown confidentiality claim does not invalidate an independently Established integrity claim about the same concept. Assess security objectives separately, and report only established claims.

5. Asset definition

Apply the following definitions.

- Two axes. Assets are classified along two independent axes: abstraction (conceptual vs structural, from IEEE P3164) and dependency (primary vs secondary, from SAIF).
- Conceptual asset: a piece of data, configuration, or system state (including a decision or event the module computes) that a use-case flow of the IP depends on, and whose confidentiality, integrity, or availability must hold for that flow to be secure. It is defined by what it means, not where it is. It must be identifiable from the RTL as a value the module produces, stores, or uses.
- Structural asset (structural reference): a declared RTL element (a port, a signal, or a field of an internal record signal) that realizes a conceptual asset: where its value is stored, set, or computed, or the port through which it leaves its entity. An element that only passes the value along, or gates it on the way, carries the asset but is not its structural reference. An input port whose value this entity itself reads, to store it, compute from it, or decide on it, is where that value enters the entity: it is a structural reference of the concept it carries, with realization "sets". Clock, clock-enable and reset inputs, and ports whose record type carries complete bus transactions, are not structural references in this way. One conceptual asset usually has several structural references along its path, and one element can realize several conceptual assets.
- Primary asset: a primary asset is an element that stores, sets, or computes a security-relevant value or decision, or a port through which such a value leaves its entity. Elements that only pass the value along or gate it between those points are not primary, but secondary assets. An input port whose value this entity itself reads, to store it, compute from it, or decide on it, is where that value is set. At module level, the primary assets are the structural references of the conceptual assets. These are what the executor reports.
- Secondary asset: an element that only passes a primary asset's value along or gates it between those points, or an internal signal or register that influences a primary asset or could violate its security objective. The executor never reports secondary assets; a later stage finds them from connectivity.
- Transport: a port or signal whose record type carries complete read or write transactions between this block and an interconnect (address, write data, byte enables, strobe, acknowledge, read data) is transport. Do not report it, whole or by field. Do not use it as the exit of a value that a register holds and software can read back, or as the element that sets a value written into this block. Report the element inside the block that stores or decides the value. A port is a single candidate: name it whole; never report a field of a port.
- Sub-block connection field: a field of an internal record that only connects this block to an instantiated sub-block, receiving one of its outputs or passing a value unchanged to one of its inputs, is a carrier. Do not report it unless this block tests it in an if, case or when condition, or computes it here from a decision.
- Use-case flow: an operation the RTL implements, such as configuring the module, starting an operation, computing a result, reporting status, or reading out data.
- Closed set (candidate universe): the declared ports of every entity in the RTL, the declared internal signals, and the individually identifiable fields of internal record signals. A port is a single candidate; its fields are not candidates. Nothing else can be a structural asset.
- Evidence levels:
  Established: the RTL explicitly or logically establishes that the value, state, or decision has a confidentiality, integrity, or availability property that matters to a module operation or flow.
  Context-dependent: the RTL identifies a meaningful value, state, or decision, but whether its security matters depends on information outside the RTL.
  Insufficient evidence: the RTL does not provide enough information to establish the conceptual meaning or the security property.
- Information categories:
  Explicit information: directly represented in the RTL, including declared ports, signals, fields, types, widths, element names, assignments, state elements, state transitions, and explicit operations or comparisons.
  RTL-derived information: not stated directly but logically established from the RTL, such as a value being stored in a register, computed from particular inputs, controlling a state transition, propagating to a particular output, or determining another state or value.
  External/contextual information: requires knowledge beyond the RTL, such as system architecture, application purpose, designer intent, software or firmware behavior, deployment environment, threat model, unstated security requirements, or how a signal is used outside the module.

Conceptual assets are identified first, from the use-case flows; their structural references are identified second. The analysis never starts by labeling individual signals as assets. A conceptual asset is reported only when its evidence level is Established.

Keep meaning separate from implementation. References implementing the same value or decision belong to its concept; different meanings may share a reference. Do not create a concept merely to justify a previously selected signal.

6. Security relevance

For each prospective concept, formulate an operation-specific property supported by a derived flow. Identify what the value or decision means, where the flow depends on it, and what violation of that property would result from disclosure, incorrect setting, or prevention of production or delivery.

Security relevance is tied to one or more of:

- Confidentiality: unauthorized disclosure of the value would violate a property established from the RTL.
- Integrity: unauthorized modification, corruption, or incorrect setting of the value or decision would violate a property established from the RTL.
- Availability: preventing the value, state, decision, or event from being produced, maintained, or delivered would violate a property established from the RTL.

Apply these tests:

- Confidentiality requires an RTL-supported restriction on disclosure or observability. A name, an absence of an output connection, or initialization to a constant does not alone establish secrecy.
- Integrity requires a demonstrated relation between the concept and the flow's correct data, configuration, state, decision, or result. Cite the particular computation, qualification, consistency relation, or state behavior that incorrect setting would violate.
- Availability requires a demonstrated requirement for a value, state, decision, or event to be produced, retained, or delivered in an implemented flow. Distinguish conditional production from an unconditional progress guarantee; do not assume external fairness or responses.

A property may be explicit in a comparison, update restriction, state rule, or other implemented behavior. It may also follow logically from data-flow and control-flow relationships. Explicit syntax is not automatically explicit security relevance: the link to a flow and objective must still be established.

An explicit security label or dedicated protection mechanism is not required when the RTL logically establishes the operation-specific integrity or availability property. Conversely, mere connectivity, influence, or the statement that a wrong signal could break the circuit is not sufficient.

Avoid generic assumptions such as “all configuration is sensitive” or “all control signals are security-critical.” Do not rank attacks, infer attacker capabilities, or search for vulnerabilities. “Unauthorized” describes the disallowed violation of the established property; it does not require or authorize inventing a threat model.

7. Evidence sufficiency

Every classification is supported by evidence from the RTL. Evidence is an explicit RTL fact or a conclusion that follows logically from identified RTL relationships; inference is an interpretation the RTL does not establish. A sufficient chain for an Established conceptual asset connects: RTL evidence, then an identifiable value, state, or decision, then its security significance, then its confidentiality, integrity, or availability objective. Element names may support interpretation but are corroborated by RTL behavior when security relevance is not explicit. Conflicting evidence is resolved conservatively; incomplete evidence leads to Context-dependent or Insufficient evidence, never to speculative completion.

A sufficient evidence annotation identifies:

- The declarations and operations supporting the value's meaning.
- The applicable flow and conditions.
- The established behavioral relation or restriction.
- How the selected objective protects that relation.
- During structural mapping, the exact declaration and its realization role.

Distinguish what the RTL guarantees under an explicit condition from what an external environment might arrange. Do not elevate possible behavior to guaranteed behavior. Consider competing drivers, branch conditions, compile-time alternatives, unreachable paths, overwrites, and invalidation where relevant.

Resolve apparent contradictions using HDL semantics and the applicable conditions. If they cannot be resolved from the supplied RTL, retain only independently supported conclusions and downgrade dependent claims. Missing behavior in a sub-block must not be completed from its name.

Final reasoning is a concise, auditable evidence summary, not a transcript of private reasoning.

8. Uncertainty

The executor uses the three evidence levels defined above, with exactly those names. Uncertainty is never resolved by assuming common hardware-security conventions. Only Established conceptual assets, and their structural references, appear in the output. Context-dependent and Insufficient evidence cases are decided during the analysis and are not reported. Not established is not the same as not present: failing to establish relevance is not evidence that an element is irrelevant.

Apply uncertainty separately to conceptual meaning, each security-objective claim, and each proposed structural reference. An Established concept does not automatically establish every possible reference or objective.

9. Analysis procedure

The stages run in this order: build the closed set; derive relationships; derive use-case flows; identify conceptual assets; identify their structural references; validate.

The executor starts from the empty output object:
{"module name": "", "conceptual assets": []}

When it identifies conceptual assets, it fills in "module name" and adds one entry per Established conceptual asset, with "related structural assets" left empty. When it moves on to structural references, it fills in each "related structural assets" list. It then validates the object. This filling happens during the analysis; the response contains only the final, completed object.

Stage descriptions:

a. Build the closed set.
Purpose: establish the only eligible structural candidates.
Input: all supplied RTL declarations.
Operation: inventory every entity, its ports, its internal signals, and identifiable internal record fields.
Output: declaration inventory with exact names and declaration owners.

b. Derive relationships.
Purpose: establish behavior before asset classification.
Input: inventory and RTL implementation.
Operation: perform the analyses in section 2 and record unresolved boundaries.
Output: evidence-linked data, control, state, and structural relationships.

c. Derive use-case flows.
Purpose: organize relationships into implemented operations.
Input: relationship model.
Operation: derive and describe flows as specified in section 3.
Output: flow descriptions with behavioral properties and conditions.

d. Identify conceptual assets.
Purpose: identify meaningful, security-relevant values before selecting elements.
Input: flows and supporting evidence.
Operation: apply sections 4–8 to each prospective concept and objective; merge descriptions of the same meaning without merging distinct decisions or values merely because they share hardware.
Output: populated conceptual entries for Established concepts, with empty structural lists.

Set "module name" using the supplied entity-instantiation structure. If it establishes an unambiguous top entity for the supplied IP, use that entity's declared name. Otherwise, use the top-level declared entity names in lexical order joined with ", " as a scope label; if the supplied structure has no identifiable roots, use the declared entity names in lexical order joined with ", ". This labeling convention does not establish an otherwise unknown architectural top and does not remove any declared entity from the closed set.

e. Identify structural references.
Purpose: locate primary realizations of each Established concept.
Input: conceptual entries, inventory, and relationship model.
Operation: trace each concept through every supplied entity and select only demonstrated realization points.

Use the realization labels as follows:

- "stores": the element retains the conceptual value or state.
- "sets": an eligible input port is read by its own entity to store, compute from, or decide on the carried value, or an internal element is an established setting point rather than a forwarding connection.
- "computes": the element realizes a computation or decision defining the concept.
- "exit port": the concept leaves its declaring entity through that port.

An exit port is eligible even when driven by a stored or computed value elsewhere in its entity, subject to the transport exclusion. An input used only for unchanged forwarding is not a setting point. Clock, clock-enable, and reset inputs do not qualify by the consumed-input rule.

Do not treat every assignment as setting, every expression as computation, or every condition operand as the decision computed by the condition. Aliases, routing selections, and gates that merely carry an already-defined value remain secondary. An influencing register is not primary unless it independently realizes an Established concept.

Apply the sub-block connection-field rule exactly. Local testing in an if, case or when condition, or computation here from a decision, removes that categorical carrier exclusion, but does not dispense with evidence of the concept and its realization. Merely reading such a field as data does not meet the exception. Testing a received field does not show that the field computes the test.

Transport is excluded whole and by field regardless of other uses. Establish transport from the record structure and transaction behavior, not particular field spellings. Do not extend this exclusion to every scalar bus-related port.

For a reference with overlapping supported roles, serialize "exit port" when the concept leaves through it; otherwise prefer "stores", then "computes", then "sets". Mention relevant overlapping behavior in the reasoning rather than duplicating the same reference under the same concept.

Output: populated structural lists. Never invent a reference to avoid an empty list. If an Established concept has no eligible structural reference in the closed set after the required exclusions, retain its empty list and briefly explain the mapping limitation.

f. Validate.
Purpose: ensure that every reported claim follows from the RTL and every reference satisfies the definitions.
Input: completed object and evidence annotations.
Operation: apply section 10, correcting unsupported classifications and mappings.
Output: final schema-conforming object.

10. Validation

Validate conceptual entries and structural mappings independently.

For each conceptual entry, check that:

- It identifies data, configuration, state, a decision, or an event produced, stored, or used by the RTL.
- It belongs to a derived use-case flow.
- Its security objective has a complete permitted-evidence basis.
- Its reasoning does not import external sensitivity, intent, software behavior, or an assumed threat model.
- Its meaning is not merely a signal name, a connectivity path, or a generic warning about malfunction.
- It is not a duplicate description of another entry's meaning.

For each structural reference, check that:

- "asset rtl" is an exact name from the closed set.
- "entity" is copied verbatim from the entity that declares it, not an instantiating parent.
- The name is bare: no entity prefix, hierarchy prefix, generated instance path, invented suffix, or expression.
- An internal record field uses its declared dot-separated signal-and-field name.
- No field of a port is reported.
- No transport element or transport field is reported.
- No carrier is reported, including unchanged sub-block connection fields that fail the specified exception.
- The realization role is demonstrated for this concept, rather than inferred from transitive influence.
- The mapping does not confuse a comparison's operand with its result or the input side of a connection with an output's computation.
- A whole internal record is not used to bypass field-level carrier or transport exclusions.

Check that all demonstrated eligible realization points were considered without adding intermediate connectivity. Recheck the RTL after any conceptual merge or split. Shared references across distinct concepts are allowed; duplicate references within the same concept are not needed.

Remove unsupported references. Downgrade unsupported conceptual claims and omit entries that are no longer Established. Do not treat absence of sufficient evidence as proof of irrelevance.

Finally check JSON syntax, exact keys, allowed enum values, module labeling, and the required empty-result form.

11. Output representation

The executor returns the EXECUTOR OUTPUT SCHEMA below and nothing else.

Use one entry per distinct Established conceptual asset. Because "security objective" is a scalar, if a concept has independently established objectives, select Confidentiality when established, otherwise Integrity when established, otherwise Availability. This is a serialization convention, not a security ranking. Include other independently established objectives and their supporting facts in "reasoning"; do not create duplicate concepts solely to repeat objectives.

Reasoning must concisely connect the concept, implemented flow, relevant RTL behavior, security objective, and realization mapping. Do not include excluded cases, speculative objectives, vulnerability assessments, or private chain-of-thought.

EXECUTOR OUTPUT SCHEMA

Return ONE JSON object and nothing else: no markdown, no code fences, no prose. Use the keys exactly as written.
{"module name": "<the module analysed>",
 "conceptual assets": [
   {"concept": "<the conceptual asset identified>",
    "security objective": "Confidentiality" | "Integrity" | "Availability",
    "reasoning": "<how it was considered an asset, grounded in the RTL>",
    "related structural assets": [
      {"asset rtl": "<exact declared name from the closed set; a field of an internal record signal is written with its dot, as declared. Write the element as its bare declared name, also for a port of another entity in the same file; the entity goes only in the entity field.>",
       "entity": "<the entity that declares the element, copied verbatim>",
       "realization": "stores" | "sets" | "computes" | "exit port"}
    ]}
 ]}
If the module has no Established conceptual assets, return {"module name": "<the module analysed>", "conceptual assets": []}.
