X1 — Role coverage
Sections edited: DEFINITIONS; 9.e. Identify structural references; 10. Validation.

Added in DEFINITIONS:
- "Role coverage: For each conceptual asset, trace its value along its path through this entity, and identify the element that plays each of these roles, when such an element exists: (a) the point where the value enters the entity or is set, meaning an input port through which it arrives, or the element that this entity's logic or software writes it into; (b) the element that holds it as state; (c) the element where a decision about it is computed; (d) the output port through which it leaves the entity."
- "Report the element for every role that exists, not only one of them."
- "Elements between these roles that only copy, synchronize, or delay the value, with no decision of their own, are carriers: they are secondary and are not reported."
- "Basis: IEEE P3164 white paper, section 3.1.2: the structural assets are "the RTL code that produces" an asset's value "and stores and transports its value"; section 4: the points where an asset "can be observed or influenced". Elements that only help transfer an asset between those points are secondary (SAIF, VTS 2021)."

Added in 9.e:
- "Apply the role coverage rule to each concept in each entity and report every existing eligible entry or setting, storage, decision, and exit realization point."

Replaced in 9.e, jointly with X2 and X6:
- Seed: "Do not report intermediates that merely forward, route, or gate an already-defined value."
- Replacement: "Do not report intermediates that only copy, synchronize, or delay an already-defined value, with no decision of their own."

Replaced in 10:
- Seed: "Check that all demonstrated eligible realization points were considered, without expanding the output to secondary connectivity."
- Replacement: "Check that all demonstrated eligible realization points for every existing entry or setting, storage, decision, and exit role are reported, without expanding the output to secondary connectivity."

X2 — Strict meaning of storage
Sections edited: DEFINITIONS; 2. Observation; 9.e. Identify structural references; 10. Validation.

Added in DEFINITIONS:
- "Storage: An element stores a value when it holds state that this entity sets or updates and keeps across clock cycles."
- "A register that only re-times, synchronizes, or delays another element's value is a carrier, not storage; report the element whose value it re-times."
- "Use the realization label "stores" only for elements that store in this sense."
- "Basis: IEEE P3164 white paper, section 3.1.2: structural assets produce, store, or transport a value; a register that only re-times a value transports it rather than storing it, and elements that only transfer an asset are secondary (SAIF)."

Replaced in 2:
- Seed: "Capturing a value in a register is storage, even if its input expression is unchanged data."
- Replacement: "Capturing a value in a register is storage only when it holds state that this entity sets or updates and keeps across clock cycles; a register that only re-times, synchronizes, or delays another element's value is a carrier, not storage."

Replaced in 9.e:
- Seed: ""stores": the element retains the concept's value or state."
- Replacement: ""stores": the element holds state that this entity sets or updates and keeps across clock cycles, rather than only re-timing, synchronizing, or delaying another element's value."
- Seed: "A storing element remains a realization point even when it captures unchanged data."
- Replacement: "A storing element remains a realization point when it holds state that this entity sets or updates and keeps across clock cycles, but a register that only re-times, synchronizes, or delays another element's value is a carrier; report the element whose value it re-times."

Replaced in 9.e, jointly with X1 and X6:
- Seed: "Do not report intermediates that merely forward, route, or gate an already-defined value."
- Replacement: "Do not report intermediates that only copy, synchronize, or delay an already-defined value, with no decision of their own."

Added in 10:
- "A "stores" reference must hold state that this entity sets or updates and keeps across clock cycles; a register that only re-times, synchronizes, or delays another element's value is a carrier, not storage."
- "Report the element whose value it re-times."

X3 — Implementation mechanics
Sections edited: DEFINITIONS; 9.d. Identify conceptual assets; 9.e. Identify structural references; 10. Validation.

Added in DEFINITIONS:
- "Implementation mechanics: An element whose only role is to sequence or time an operation, such as a bit or cycle counter that advances a shift, a handshake or strobe pulse, a flag used only for pacing, or a clock-enable tick, is implementation mechanics."
- "It is not a primary asset unless the RTL shows that it holds or decides a security-relevant value, for example a counter whose value decides a timeout or a lockout."
- "Basis: SAIF defines primary assets as what designers "esteem ... as a definitive target for protection" (its examples are keys, random numbers and seeds, identifiers, private data, and configuration bits for operational and privilege modes); LAsset defines them as "the direct target of an attack"."

Added in 9.d:
- "Exclude implementation mechanics whose only role is to sequence or time an operation, unless the RTL shows that they hold or decide a security-relevant value."

Added in 9.e:
- "Do not report elements whose only role is to sequence or time an operation unless the RTL shows that they hold or decide a security-relevant value."

Added in 10:
- "Implementation mechanics must be excluded unless the RTL shows that they hold or decide a security-relevant value."

No seed sentence was replaced or removed solely for X3. The former blanket clock-enable exclusions are replaced under X5 and X7; clock-enable ticks are addressed by the implementation-mechanics rule above.

- Replacement: "Shared access paths: A shared bus or register-access interface (address, write data, byte enables, strobe, acknowledge, read data) and the decoding around it are the path through which software reaches this entity's registers."

X5 — Clock and reset infrastructure
Sections edited: DEFINITIONS; 9.e. Identify structural references; 10. Validation.

Added in DEFINITIONS:
- "Clock and reset infrastructure: Global clock and reset inputs are infrastructure that interacts with every register of the entity; they are secondary, not primary assets of this entity."
- "The exception is an entity whose function is to produce or control a clock or a reset: there, the clock and reset elements that implement that function are structural references of it."
- "Basis: SAIF: secondary assets are "infrastructures that closely interact with the primary assets"; CWE-1206 (Power, Clock, Thermal, and Reset Concerns) treats clock and reset control as a security concern."

Replaced in DEFINITIONS, jointly with X4 and X7:
- Seed: "Clock, clock-enable and reset inputs, and ports whose record type carries complete bus transactions, are not structural references in this way."
- Replacement: "Ports covered by the shared access path or clock and reset infrastructure rules follow those rules."

Replaced in 9.e:
- Seed: "Clock, clock-enable, and reset inputs are not structural references under the consumed-input rule."
- Replacement: "Global clock and reset inputs are secondary infrastructure, except that, in an entity whose function is to produce or control a clock or a reset, the clock and reset elements that implement that function are structural references of it."

Added in 10:
- "Global clock and reset inputs must be excluded unless they implement this entity's function of producing or controlling a clock or a reset."
