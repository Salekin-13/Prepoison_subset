1. Information

The methodology is independent of any RTL instance. The executor receives only the RTL of one hardware IP module, with all comments removed. The RTL may declare more than one entity. The RTL is the sole authoritative source for the analysis. Comments are not a source of evidence, because the input has none.

Distinguish these information categories:
- Explicit information: directly represented in the RTL, including declared ports, signals, fields, types, widths, element names, assignments, state elements, state transitions, and explicit operations or comparisons.
- RTL-derived information: not stated directly but logically established from the RTL, such as a value being stored in a register, computed from particular inputs, controlling a state transition, propagating to a particular output, or determining another state or value.
- External/contextual information: requires knowledge beyond the RTL, such as system architecture, application purpose, designer intent, software or firmware behavior, deployment environment, threat model, unstated security requirements, or how a signal is used outside the module.

Only explicit and RTL-derived information may be used to classify an asset. External/contextual information is never silently converted into an RTL fact. If the security relevance of an element depends on unavailable external information, that dependency is treated as Context-dependent, not assumed.

The analysis answers, in order: what is explicitly present in the RTL; what can be logically established from it; what remains unknown because it needs external context.

Language semantics may be used to interpret the RTL. They do not supply missing application requirements, authority relationships, or security intent. Keep concise working records of observations, derived relationships, and unresolved dependencies. The final response provides grounded evidence summaries, not private deliberation.

2. Observation

Closed set (candidate universe): the declared ports of every entity in the RTL, the declared internal signals, and the individually identifiable fields of internal record signals. Nothing else can be a structural asset.

The executor first builds the closed set, recording for each element its exact declared name and the entity that declares it. Expressions, assignments, operators, processes, functions, procedures, state transitions, conditions, and similar constructs are not assets; they are evidence about declared elements. The executor derives relationships from the RTL before classifying anything, and distinguishes a value's origin or realization point from the intermediate elements it later travels through.

For the inventory:
- Record declaration kind, direction where applicable, type, width, record structure, and declaring entity.
- Associate architecture-level declarations with their owning entity. Preserve declaration spelling and case.
- Preserve record-field paths using the declared signal and field names separated by dots. Do not invent bit-slice, expression, instance-path, or operation names as candidates.
- Retain scope information for interpreting repeated local names without replacing exact declared names with invented identifiers.
- Include declarations from every supplied entity, not merely entities reachable from an assumed top.

Derive relationships using:
- Driver/use analysis and assignment semantics, including guarded assignments, record updates, and partial assignments.
- Forward and backward data-flow tracing through copies, routing, arithmetic, Boolean operations, comparisons, transformations, and visible function or procedure bodies.
- Control-dependency analysis linking guards and decisions to updates, transitions, acceptance, suppression, and output behavior.
- State analysis identifying storage, retained values, initialization, reset behavior, update conditions, and state transitions.
- Structural analysis of declared interface directions, locally visible instantiations, and port connections.
- Output tracing identifying where values leave each entity, including intermediate entity boundaries.
- Semantic distinctions among storage, genuine value or decision formation, and mere transport or gating.

Assignment syntax alone does not establish a realization point. A destination receiving a copied or gated value is not thereby the place where that value is set or computed. Conversely, storage of a value is a realization point even when the stored value was computed elsewhere.

Resolve parameters and elaboration conditions only as supported by the supplied RTL. Preserve unresolved alternatives rather than assuming an external configuration. An unavailable entity body or function body is an opaque boundary; its behavior must not be invented.

The output of this stage is an evidence-backed relationship model connecting declared elements to values, computations, decisions, state, guards, and entity exits. It contains no asset classifications.

3. Use-case flows

Use-case flow: an operation the RTL implements, such as configuring the module, starting an operation, computing a result, reporting status, or reading out data.

Before identifying conceptual assets, the executor derives the module's use-case flows from the RTL alone.

Recognize flows by following implemented operations from their entry conditions or input consumption through computation, state changes, and observable completion or output. Use control and data dependencies to identify coherent operations. A combinational operation is a flow even without a start event or stored state.

Describe each flow internally using:
- The declaring entities and RTL-visible scope involved.
- Entry conditions, consumed values, and relevant pre-existing state.
- The implemented computation or sequence of guarded updates.
- Decisions that determine acceptance, progression, commitment, rejection, or delivery.
- Produced values, state changes, events, and exit ports.
- Completion conditions and dependencies on externally supplied inputs.

Use behavioral descriptions supported by the RTL. Do not name a flow after a presumed application, software transaction, or security purpose. A name suggesting a familiar operation may guide inspection but does not establish that interpretation.

Separate what a flow implements from what outside agents might do with its outputs. The resulting flow descriptions provide the semantic starting point for conceptual-asset identification.

4. External information

Conclusions requiring external information include:
- Who is authorized to observe or modify a value, unless the RTL itself represents the relevant distinction.
- Whether an otherwise ordinary value is confidential or security-sensitive in a deployment.
- The purpose, trust level, or privilege of an external interface.
- Whether external software follows a particular sequence or interpretation.
- Whether an output controls a security-sensitive resource outside the supplied RTL.
- Whether external inputs satisfy fairness, timing, reset, or protocol assumptions not established in the RTL.
- The behavior of unavailable implementations and unstated properties of presumed algorithms.

Record the missing dependency without filling it in. If the RTL identifies a meaningful value but establishing its security relevance requires that dependency, classify the conceptual candidate as Context-dependent. If unavailable implementation details prevent identifying its meaning or supporting the proposed property, use Insufficient evidence.

An RTL-visible input condition may qualify a local claim: the executor may describe behavior under that condition without asserting that the environment guarantees it. Likewise, a visible local access restriction may support a local decision property without establishing a system-wide authorization policy.

Do not invent missing information. Do not perform vulnerability discovery, exploitability analysis, or threat assessment. A dependency may be examined only as needed to define asset relevance.

5. Asset definition

Apply these definitions:

- Two axes. Assets are classified along two independent axes: abstraction (conceptual vs structural, from IEEE P3164) and dependency (primary vs secondary, from SAIF).
- Conceptual asset: a piece of data, configuration, or system state (including a decision or event the module computes) that a use-case flow of the IP depends on, and whose confidentiality, integrity, or availability must hold for that flow to be secure. It is defined by what it means, not where it is. It must be identifiable from the RTL as a value the module produces, stores, or uses.
- Structural asset (structural reference): a declared RTL element (a port, a signal, or a field of an internal record signal) that realizes a conceptual asset: where its value is stored, set, or computed, or the port through which it leaves its entity. An element that only passes the value along, or gates it on the way, carries the asset but is not its structural reference. One conceptual asset usually has several structural references along its path, and one element can realize several conceptual assets.
- Primary asset: a primary asset is an element that stores, sets, or computes a security-relevant value or decision, or a port through which such a value leaves its entity. Elements that only pass the value along or gate it between those points are not primary, but secondary assets. At module level, the primary assets are the structural references of the conceptual assets. These are what the executor reports.
- Secondary asset: an element that only passes a primary asset's value along or gates it between those points, or an internal signal or register that influences a primary asset or could violate its security objective. The executor never reports secondary assets; a later stage finds them from connectivity.

Conceptual assets are identified first, from the use-case flows; their structural references are identified second. The analysis never starts by labeling individual signals as assets. A conceptual asset is reported only when its evidence level is Established.

Define concepts by their flow-level meaning. Do not create separate conceptual assets merely because the same value has different signal names or storage locations. Distinguish semantically different values or decisions when the RTL establishes their separate roles. An element may realize different concepts.

For structural mapping, distinguish:
- stores: the element retains the conceptual value as state.
- sets: the element is a genuine establishment point for the conceptual value or event, not an alias or a transport gate.
- computes: the element holds the result of logic that derives the conceptual value or decision.
- exit port: the value leaves the element's declaring entity through that port.

A selection, gate, slice, concatenation, or assignment does not automatically compute a conceptual asset. Determine whether it establishes the meaning-bearing value or merely transports an already established value. A separately computed permission or validation decision may itself be a conceptual asset; the intermediate payload wire controlled by it remains a carrier unless it independently satisfies a realization role.

An outward-facing port is an eligible exit reference even when its driver only forwards the value. An incoming port is not a reference merely because it admits a value. Neither direction nor naming establishes security relevance.

A dependency or carrier for a concept may independently realize another Established concept. Do not promote supporting clocks, resets, enables, counters, or other influences solely because they can affect a primary asset.

6. Security relevance

For each conceptual candidate, identify a concrete property of an RTL-derived flow and determine whether the candidate's protection matters to that property.

Security relevance is tied to one or more of:
- Confidentiality: unauthorized disclosure of the value would violate a property established from the RTL.
- Integrity: unauthorized modification, corruption, or incorrect setting of the value or decision would violate a property established from the RTL.
- Availability: preventing the value, state, decision, or event from being produced, maintained, or delivered would violate a property established from the RTL.

Use the following decision test:
- Identify the value's meaning and its role in an implemented flow.
- Identify the specific disclosure restriction, permitted-state or update constraint, validation or acceptance rule, security-relevant consistency condition, or production/delivery obligation supported by the RTL.
- Explain how disclosure, alteration, or withholding of that value would violate the identified property.
- Check whether any link requires an unstated external fact.

These are forms of evidence, not a required mechanism checklist. A dedicated security block, security-labelled name, or particular implementation style is not required. A logically established property of a flow may suffice. However, simple functional dependence does not by itself establish security relevance: “this affects an output” or “corruption changes the result” is not a complete security-significance argument.

Distinguish:
- Explicit relevance: the RTL directly represents the relevant restriction, check, state rule, or obligation and the candidate's role in it.
- RTL-derived relevance: the significance follows from traced RTL relationships, such as a computed decision determining whether a constrained update or release occurs.
- Context-dependent relevance: the meaning is identifiable, but its security significance needs an external requirement, role, or use.

For Confidentiality, identify the RTL-grounded disclosure property and the value it covers. A value being internal, named suggestively, transformed, or absent from an output does not alone establish secrecy. A generic validity gate does not automatically establish an authorization boundary.

For Integrity, identify the established rule whose validity depends on the value or decision. Do not assume that every configuration item or control signal is security-critical.

For Availability, identify the security-relevant obligation to produce, maintain, or deliver the value or event. Do not infer timing guarantees, environmental cooperation, or fairness that the RTL does not establish. Mere stalling capability is not sufficient.

Establish that the objective matters; do not require proof that the design perfectly enforces it. A possible defect does not automatically erase an otherwise established asset. Conversely, do not claim a global guarantee from a local check.

7. Evidence sufficiency

Every classification is supported by evidence from the RTL. Evidence is an explicit RTL fact or a conclusion that follows logically from identified RTL relationships; inference is an interpretation the RTL does not establish.

A sufficient chain for an Established conceptual asset connects: RTL evidence, then an identifiable value, state, or decision, then its security significance, then its confidentiality, integrity, or availability objective.

Element names may support interpretation but are corroborated by RTL behavior when security relevance is not explicit. Conflicting evidence is resolved conservatively; incomplete evidence leads to Context-dependent or Insufficient evidence, never to speculative completion.

A sufficient evidence record identifies:
- The declarations, operations, assignments, or state rules supporting the conceptual meaning.
- The relevant data or control path within a derived flow.
- The concrete property that makes protection of the value matter.
- The supported objective and the consequence of its violation.
- During structural mapping, the realization role of each reported reference.

Logical derivations must respect guards, widths, update semantics, resets, alternative assignments, and visible hierarchy. An interpretation that depends on a familiar signal name, presumed algorithm, unseen consumer, or unstated trust boundary is not an RTL derivation.

Check competing drivers, alternate paths, and reachable behaviors relevant to the proposed claim. If they contradict the claim, narrow it to what is supported or reject Established status. A contradiction to a claimed implementation guarantee need not contradict the existence or security significance of a represented decision; assess those claims separately.

Use Context-dependent when the meaningful value is established but security significance needs outside context. Use Insufficient evidence when the available RTL cannot establish the proposed meaning or property, including unresolved implementation ambiguity. Do not repair either case by assuming common hardware-security conventions.

Final reasoning is a concise audit summary of facts and their relevance, not a transcript of private chain-of-thought.

8. Uncertainty

Use exactly these evidence levels:
- Established: the RTL explicitly or logically establishes that the value, state, or decision has a confidentiality, integrity, or availability property that matters to a module operation or flow.
- Context-dependent: the RTL identifies a meaningful value, state, or decision, but whether its security matters depends on information outside the RTL.
- Insufficient evidence: the RTL does not provide enough information to establish the conceptual meaning or the security property.

Uncertainty is never resolved by assuming common hardware-security conventions. Only Established conceptual assets, and their structural references, appear in the output. Context-dependent and Insufficient evidence cases are decided during the analysis and are not reported.

Not established is not the same as not present: failing to establish relevance is not evidence that an element is irrelevant.

Keep unresolved external dependencies and implementation gaps in the working analysis. Do not add an uncertainty list, rejected-candidate list, confidence score, or secondary-asset list to the response.

9. Analysis procedure

The stages run in this order: build the closed set; derive relationships; derive use-case flows; identify conceptual assets; identify their structural references; validate.

Start from the empty output object:
{"module name": "", "conceptual assets": []}

Build the closed set.
Purpose: establish the only eligible structural-reference universe.
Input: the supplied RTL.
Operation: inventory declarations and ownership as specified in Observation.
Output: the closed set and declaration metadata. Do not label assets.

Derive relationships.
Purpose: distinguish value realization from transport and establish behavior.
Input: the RTL and closed set.
Operation: perform the data-flow, control-flow, state, and structural analyses.
Output: evidence-backed relationships and unresolved implementation boundaries.

Derive use-case flows.
Purpose: establish implemented operations before conceptual identification.
Input: the relationship model.
Operation: trace coherent input/state-to-operation-to-outcome behavior.
Output: flow descriptions with their conditions, decisions, state effects, and outputs.

Identify conceptual assets.
Purpose: identify meaning-bearing values whose security relevance is Established.
Input: the flows and supporting relationships.
Operation: define concepts; apply the relevance and sufficiency tests; distinguish the evidence levels; consolidate concepts by meaning rather than signal name.
Output: fill in "module name" and add one entry per Established conceptual asset, leaving "related structural assets" empty.

Use the unique module identity established by declarations and visible hierarchy for "module name". If the supplied RTL does not establish a unique module identity, use an empty string rather than inventing or guessing a top entity. This naming uncertainty does not exclude any declared entity from analysis. Resolve the name even when no conceptual assets are Established.

Identify structural references.
Purpose: locate primary realization points for the Established concepts.
Input: the conceptual entries, closed set, and relationship model.
Operation: trace each conceptual value across its supported flow and entity boundaries; identify where it is stored, set, computed, or exits; reject mere carriers and influences.
Output: populate each "related structural assets" list with its eligible references.

Do not force a reference where the value is only used or carried within the supplied RTL. If an Established concept has no eligible realization point in the closed set, leave its list empty rather than promote a secondary asset or invent an external declaration.

Validate.
Purpose: ensure semantic, evidentiary, structural, and schema consistency.
Input: the completed working object and all supporting RTL evidence.
Operation: apply the checks in Validation.
Output: the final JSON object only.

This filling happens during the analysis; the response contains only the final, completed object.

10. Validation

Validate each conceptual entry against the supplied RTL:
- Its meaning is identifiable as a value, state, decision, or event the module produces, stores, or uses.
- It belongs to a flow derived before conceptual identification.
- Its security objective has a complete RTL-grounded evidence chain.
- Its reasoning does not convert an external assumption into a fact.
- Its claims remain valid under relevant guards, resets, assignments, and visible alternative paths.
- Its conceptual identity is not merely a renamed location or an unjustified merger of different values.
- Its presence does not depend on proving exploitability or a vulnerability.

Validate each structural reference:
- "asset rtl" is an exact name from the closed set.
- "entity" is copied verbatim from the declaring entity.
- The element realizes the listed concept, not merely another value that influences it.
- The assigned realization is supported by storage behavior, semantic establishment, computation, or outward port behavior.
- No carrier is reported as a structural reference. Outward ports qualify under the explicit exit-port rule; internal forwarding wires do not.
- Record fields are correctly identified. Aggregate containment alone is not sufficient justification for an aggregate reference.
- References are not missing solely because a value crossed an entity boundary, and declarations outside the supplied RTL have not been invented.

Use a canonical realization label when an element has overlapping roles: prefer "exit port" for a port through which the value leaves its entity; otherwise "stores" for retained state; otherwise "computes" for a derived value or decision; otherwise "sets" for genuine nonforwarding establishment. This affects representation, not eligibility.

Validate the object:
- Every listed concept is Established.
- Every listed objective is supported.
- Related references are deduplicated within the concept without merging different concepts.
- Empty reference lists have not resulted from an unperformed mapping stage.
- No secondary assets or excluded evidence-level cases appear.
- Keys, value types, and permitted enumerations match the schema.
- The response contains no material outside the JSON object.

11. Output representation

The executor returns the EXECUTOR OUTPUT SCHEMA reproduced in the execution prompt below and nothing else.

Use one entry per Established conceptual asset. Because "security objective" is singular, select "Confidentiality" when it is Established for that concept; otherwise select "Integrity" when Established; otherwise select "Availability". Describe any additional Established objectives concisely in "reasoning". This is a serialization convention, not a priority rule for deciding relevance, and must not create duplicate conceptual entries.

The "reasoning" field states the implemented flow, the relevant RTL facts and logically derived relationships, the security significance, and the basis for the structural mapping. It must not contain unsupported application stories, private deliberation, or lists of rejected candidates.

Use exact declared names for structural references and exact declaring-entity names. Do not add fields for evidence levels, secondary assets, vulnerabilities, uncertainty, or analysis stages.

If no conceptual assets are Established, return the schema's empty conceptual-assets object with the module identity resolved under the naming rule.
