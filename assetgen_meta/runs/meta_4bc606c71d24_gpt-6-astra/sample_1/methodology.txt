1. Information

The executor receives only the RTL of one hardware IP module, with all comments removed. The RTL may declare more than one entity. The RTL is the sole authoritative source for the analysis. Comments are not a source of evidence.

The executor distinguishes the three information categories defined below. Only explicit and RTL-derived information may be used to classify an asset. External/contextual information is never silently converted into an RTL fact. If the security relevance of an element depends on unavailable external information, that dependency is treated as Context-dependent, not assumed. The analysis answers, in order: what is explicitly present in the RTL; what can be logically established from it; what remains unknown because it needs external context.

Maintain evidence annotations that distinguish observed declarations and operations from relationships logically derived from them. Record unresolved contextual dependencies during analysis, but do not include unestablished candidates in the response.

The task is asset identification, not vulnerability discovery, exploitability analysis, or threat assessment. Do not infer that identifying an asset proves either that the RTL protects it or that a vulnerability exists.

2. Observation

The executor first builds the closed set, recording for each element its exact declared name and the entity that declares it. Expressions, assignments, operators, processes, functions, procedures, state transitions, conditions, and similar constructs are not assets; they are evidence about declared elements. The executor derives relationships from the RTL before classifying anything, and distinguishes a value's origin or realization point from the intermediate elements it later travels through.

Build a declaration inventory covering every entity in the supplied RTL. Associate architectures or other implementation bodies with their owning entities where the RTL establishes that association. Record declaration scope internally so that repeated local names are not confused. An instance name is not the name of the entity declaring an element.

For each candidate, record applicable RTL facts:
- Exact declared identifier, declaring entity, port direction, type, width, record structure, and array structure.
- Drivers, assignments, readers, and supplied-RTL instance connections.
- Whether its value is combinational, retained as state, initialized, reset, conditionally updated, or explicitly invalidated.
- Assignment guards, update priorities, comparison operands, state-transition dependencies, and output connections.
- Declaration and elaboration conditions that affect whether the element or behavior exists.

Internal record fields use the declared signal and field identifiers in their dotted form. Do not invent candidates for slices, indexed accesses, expressions, constants, parameters, type declarations, or other constructs outside the closed set. Use a declared aggregate when no separately eligible declared element represents the accessed portion.

Derive a relationship model containing:
- Data dependence: which values are copied, selected, transformed, combined, compared, stored, or delivered.
- Control dependence: which conditions govern computation, update, retention, transition, acceptance, rejection, or delivery.
- State dependence: how prior state, reset behavior, and update rules determine later state.
- Structural dependence: connections between declared elements, entity boundaries, and supported record-field relationships.
- Semantic correspondence: whether different elements represent the same meaningful value, a different encoding of it, or a distinct result or decision.

Distinguish direct computation or state establishment from forwarding, selection used only for transport, representation-preserving wiring, and delivery gating. An operator appearing in an assignment does not by itself make the destination a realization point. Conversely, a state element can store a conceptual value even when its update copies that value from elsewhere.

Analyze supplied function or procedure bodies as evidence when available, without treating those constructs as candidates. Do not assume the behavior of missing entities, unresolved functions, or external implementations. Exclude behavior as unreachable only when the supplied RTL logically establishes that exclusion.

The output of observation is the closed set and an evidence-annotated relationship model, not an asset classification.

3. Use-case flows

Before identifying conceptual assets, the executor derives the module's use-case flows from the RTL alone.

Recognize flows by tracing connected behavior that implements an operation. Relevant evidence includes input sampling, configuration updates, request acceptance, state progression, transformations, explicit checks, result retention, status generation, and output delivery. Continuous combinational behavior may implement a flow without a request, clocked sequence, or completion flag.

Describe each flow using:
- The operation implemented, using terminology supported by behavior rather than presumed application purpose.
- Its entry conditions, participating values, and relevant prior state.
- Its transformations, decisions, update rules, and state progression.
- Its observable result, retained state, reported status, or RTL-defined completion or delivery event.
- The relationships and RTL operations establishing the description.
- Any missing behavior or context that limits what can be concluded.

Do not require a particular interface protocol or infer software transactions from an interface name. If the RTL establishes only part of an operation, describe that part without inventing the surrounding system flow.

Flows should expose what values, decisions, and states the operation depends on. They are not lists of signals relabeled as operations.

4. External information

Conclusions needing external information include application-level secrecy, external trust boundaries, authorized users, software policy, deployment requirements, unstated timing guarantees, the purpose of externally supplied data, and how another component uses an output. Names suggesting such meanings do not establish those conclusions.

For each missing dependency, identify internally:
- What the RTL does establish.
- The specific fact required to establish the proposed security relevance.
- Whether the gap concerns security significance or the underlying meaning and behavior.

Use Context-dependent when the RTL identifies a meaningful value, state, or decision but its security importance requires an external fact. Use Insufficient evidence when the available RTL does not sufficiently establish the conceptual meaning or a security property.

Do not supply missing facts from hardware-security conventions, familiar interface names, presumed algorithms, likely software behavior, or expected system architecture. Missing implementations and unresolved elaboration conditions remain limitations. A conditional conclusion may be Established when the condition and the claimed relationship are themselves established by the RTL; state that scope explicitly rather than assuming the condition holds.

If the supplied hierarchy identifies an enclosing IP entity unambiguously, use its exact declared name as the module name. Otherwise, use the applicable declared root-entity names in source order, joined with “ / ”, as a scope label rather than inventing an enclosing entity. If root determination is itself unresolved, use the supplied entity names in source order as that scope label. Naming the analysis scope does not remove any supplied entity from the closed set.

5. Asset definition

Apply these definitions:

- Two axes. Assets are classified along two independent axes: abstraction (conceptual vs structural, from IEEE P3164) and dependency (primary vs secondary, from SAIF).
- Conceptual asset: a piece of data, configuration, or system state (including a decision or event the module computes) that a use-case flow of the IP depends on, and whose confidentiality, integrity, or availability must hold for that flow to be secure. It is defined by what it means, not where it is. It must be identifiable from the RTL as a value the module produces, stores, or uses.
- Structural asset (structural reference): a declared RTL element (a port, a signal, or a field of an internal record signal) that realizes a conceptual asset: where its value is stored, set, or computed, or the port through which it leaves its entity. An element that only passes the value along, or gates it on the way, carries the asset but is not its structural reference. One conceptual asset usually has several structural references along its path, and one element can realize several conceptual assets.
- Primary asset: a primary asset is an element that stores, sets, or computes a security-relevant value or decision, or a port through which such a value leaves its entity. Elements that only pass the value along or gate it between those points are not primary, but secondary assets. At module level, the primary assets are the structural references of the conceptual assets. These are what the executor reports.
- Secondary asset: an element that only passes a primary asset's value along or gates it between those points, or an internal signal or register that influences a primary asset or could violate its security objective. The executor never reports secondary assets; a later stage finds them from connectivity.
- Use-case flow: an operation the RTL implements, such as configuring the module, starting an operation, computing a result, reporting status, or reading out data.
- Closed set (candidate universe): the declared ports of every entity in the RTL, the declared internal signals, and the individually identifiable fields of internal record signals. Nothing else can be a structural asset.
- Evidence levels:
  Established: the RTL explicitly or logically establishes that the value, state, or decision has a confidentiality, integrity, or availability property that matters to a module operation or flow.
  Context-dependent: the RTL identifies a meaningful value, state, or decision, but whether its security matters depends on information outside the RTL.
  Insufficient evidence: the RTL does not provide enough information to establish the conceptual meaning or the security property.
- Information categories:
  Explicit information: directly represented in the RTL, including declared ports, signals, fields, types, widths, element names, assignments, state elements, state transitions, and explicit operations or comparisons.
  RTL-derived information: not stated directly but logically established from the RTL, such as a value being stored in a register, computed from particular inputs, controlling a state transition, propagating to a particular output, or determining another state or value.
  External/contextual information: requires knowledge beyond the RTL, such as system architecture, application purpose, designer intent, software or firmware behavior, deployment environment, threat model, unstated security requirements, or how a signal is used outside the module.

Conceptual assets are identified first, from the use-case flows; their structural references are identified second. The analysis never starts by labeling individual signals as assets. A conceptual asset is reported only when its evidence level is Established.

Describe a concept by its RTL-supported meaning and role in a flow, independently of its eventual declaration names. Group realizations that have the same conceptual meaning. Do not merge distinct decisions or values merely because they are connected, and do not split a concept merely because it traverses different declarations.

6. Security relevance

Evaluate each proposed concept against an operation-specific property and a confidentiality, integrity, or availability objective:

- Confidentiality: unauthorized disclosure of the value would violate a property established from the RTL.
- Integrity: unauthorized modification, corruption, or incorrect setting of the value or decision would violate a property established from the RTL.
- Availability: preventing the value, state, decision, or event from being produced, maintained, or delivered would violate a property established from the RTL.

The executor avoids generic assumptions such as “all configuration is sensitive” or “all control signals are security-critical”.

For each proposed objective, identify:
- The meaningful value, state, decision, or event.
- The flow that depends on it.
- The concrete property of that flow established by the RTL.
- Why disclosure, incorrect value or setting, or absence would violate that property.

Distinguish the evidentiary basis:
- Explicit relevance is grounded directly in RTL-represented restrictions, decisions, checks, operations, or state rules.
- RTL-derived relevance follows logically from identified behavior and dependencies, even if no declaration labels the value as security-related.
- Context-dependent relevance requires an unstated purpose, policy, trust relationship, or external consequence.

For Confidentiality, establish a value-specific non-disclosure or restricted-disclosure property from the RTL. A suggestive name, transformation resembling cryptography, or absence of an output connection does not alone establish secrecy. Do not invent an unauthorized observer.

For Integrity, establish what correctness or setting of the value means for the implemented operation and what RTL-established result, decision, constraint, or state relation depends on it. An ordinary functional value is not automatically excluded, and an explicit security mechanism is not mandatory. However, “changing this can affect something” is not an operation-specific security justification.

For Availability, establish the relevant production, retention, progression, completion, or delivery property and its dependence on the concept. Do not infer a deadline, unconditional progress, or resistance to external disruption that the RTL does not establish. A signal's presence in an enable path is not sufficient to make it an availability asset.

A check or gate is not automatically an authorization mechanism. Describe its actual RTL-established decision unless further semantics are established. Likewise, a controlling element is not primary merely because it can influence an established asset.

7. Evidence sufficiency

Every classification is supported by evidence from the RTL. Evidence is an explicit RTL fact or a conclusion that follows logically from identified RTL relationships; inference is an interpretation the RTL does not establish. A sufficient chain for an Established conceptual asset connects: RTL evidence, then an identifiable value, state, or decision, then its security significance, then its confidentiality, integrity, or availability objective. Element names may support interpretation but are corroborated by RTL behavior when security relevance is not explicit. Conflicting evidence is resolved conservatively; incomplete evidence leads to Context-dependent or Insufficient evidence, never to speculative completion.

Maintain an evidence record for each proposed concept containing its flow, semantic meaning, relevant operations and relationships, claimed property, objective, and evidence level. After conceptual classification, add evidence for each proposed realization role.

Evidence is sufficient when:
- The concept corresponds to a value the module demonstrably produces, stores, or uses.
- Its meaning is supported by operations or state behavior, not merely a suggestive identifier.
- The claimed security significance is specific to an established flow property.
- The connection from a violation of the selected objective to that property follows from the RTL.
- Each eventual structural reference independently meets a realization definition.

Connectivity establishes dependence, not automatically conceptual meaning or security importance. A state declaration establishes storage, not automatically sensitivity. An output connection establishes an exit role only after the conceptual value and security relevance have been established.

Resolve conflicts by examining assignment priority, guards, reachability, alternate drivers, conditional elaboration, and contrary uses. If the full behavior supports only a narrower property, narrow the claim to that supported property. If a conflict prevents the claimed property from being established, downgrade the candidate.

Do not claim simulation, formal proof, elaboration results, or inaccessible source evidence that was not actually available. The final “reasoning” text is a concise evidence justification, not a transcript of private deliberation.

8. Uncertainty

The executor uses the three evidence levels defined above, with exactly those names. Uncertainty is never resolved by assuming common hardware-security conventions. Only Established conceptual assets, and their structural references, appear in the output. Context-dependent and Insufficient evidence cases are decided during the analysis and are not reported. Not established is not the same as not present: failing to establish relevance is not evidence that an element is irrelevant.

9. Analysis procedure

The stages run in this order: build the closed set; derive relationships; derive use-case flows; identify conceptual assets; identify their structural references; validate.

The executor starts from the empty output object:
{"module name": "", "conceptual assets": []}

When it identifies conceptual assets, it fills in "module name" and adds one entry per Established conceptual asset, with "related structural assets" left empty. When it moves on to structural references, it fills in each "related structural assets" list. It then validates the object. This filling happens during the analysis; the response contains only the final, completed object.

Build the closed set.
- Purpose: establish the complete eligible declaration universe.
- Input: supplied comment-free RTL.
- Operation: inventory every entity's eligible ports, internal signals, and internal record fields, preserving exact names and ownership.
- Output: the closed set, declaration metadata, and unresolved declaration conditions.

Derive relationships.
- Purpose: establish what the declared elements do without classifying assets.
- Input: the closed set and supplied RTL bodies.
- Operation: perform the data-flow, control-flow, state, structural, and semantic-correspondence analysis in section 2.
- Output: evidence-annotated relationships, including distinctions between realization and transport behavior.

Derive use-case flows.
- Purpose: establish the implemented operations from which concepts can be identified.
- Input: the relationship model and explicit RTL operations.
- Operation: construct the flow descriptions in section 3.
- Output: RTL-supported flow descriptions and their limitations.

Identify conceptual assets.
- Purpose: identify meaningful values with Established security objectives.
- Input: flows and their supporting evidence, not a preclassified signal list.
- Operation: identify proposed concepts; apply the significance and sufficiency tests; assign Established, Context-dependent, or Insufficient evidence; consolidate concepts by meaning.
- Output: the module name and conceptual entries for Established concepts, each with an empty structural-reference list and an evidence-grounded explanation.

The schema provides a scalar “security objective”. If a concept has different Established objectives, select the objective with the most direct and complete RTL support and describe any additional Established objectives in “reasoning”. Resolve otherwise indistinguishable choices in the order Confidentiality, Integrity, Availability. Do not duplicate a conceptual asset solely to encode different objectives.

Identify their structural references.
- Purpose: locate the primary realizations of each Established concept within the closed set.
- Input: Established conceptual assets, the closed set, and the relationship model.
- Operation: trace each concept through supported relationships and test candidate elements for these roles:
  - stores: the element retains the conceptual value as RTL state.
  - sets: the element directly establishes the conceptual value or decision, rather than merely enabling another element to establish it.
  - computes: the element holds the result of an operation that determines the conceptual value or decision, rather than merely routing it.
  - exit port: the port carries the conceptual value out of its declaring entity.

An outward port is an exit realization even when driven by a direct connection. It is not merely an intermediate carrier because it is an entity exit point under the definitions. Apply this rule to every supplied entity, not just the enclosing entity. For a bidirectional port, require RTL evidence of the relevant outward use.

A port's being an input does not itself establish any realization role. Neither external driving nor downstream influence alone proves that an input stores, sets, or computes the concept.

A combinational copy or transport-only gate is not a setter or computation of the carried concept. A signal that computes a gate's decision can be a structural reference of a separately Established decision concept, but that does not make it a structural reference of all values it gates.

Do not include a control, reset, enable, intermediate register, or other dependency merely because it can affect the asset. A retained instance of the conceptual value itself qualifies as storage; a register holding only a controlling dependency does not thereby qualify.

For the “realization” field, prefer exit port for outward ports; otherwise use stores for retained state, computes for semantic computation, and sets for direct establishment without those other roles. Explain any additionally relevant role in the evidence justification rather than duplicating the same mapping.

Map a record field when the concept is realized by that field. Map the enclosing record only if the record as an aggregate independently realizes the concept; containment alone is insufficient. Never fabricate a reference or promote a carrier to fill a list.

- Output: structural-reference lists containing only exact closed-set elements with supported realization roles.

Validate.
- Purpose: ensure the completed object is faithful to the RTL, definitions, and schema.
- Input: the completed object and its evidence records.
- Operation: apply section 10; remove or correct unsupported claims without inventing missing evidence.
- Output: the final JSON object.

If no conceptual assets are Established, still fill in the module name before returning the empty conceptual-assets list. Any correction requiring new analysis must respect the same stage dependencies.

10. Validation

Validate the completed object against the RTL and the following checks:

- Scope: the analysis considered the eligible declarations of every supplied entity and did not silently restrict itself to an assumed top-level interface.
- Concept-first identification: each concept comes from a supported use-case flow, rather than from a sensitive-looking declaration name.
- Meaning: each concept is identifiable as a value, state, decision, or event produced, stored, or used by the module.
- Evidence: the explanation connects identifiable RTL operations and relationships to an operation-specific property and the selected objective.
- Authority: no application purpose, external policy, threat model, missing implementation, or conventional hardware assumption has been promoted into an RTL fact.
- Evidence level: every reported concept is Established; uncertainty cases and secondary assets are absent.
- Names: each “asset rtl” is an exact name from the closed set, using the required dotted representation for internal record fields.
- Ownership: each “entity” is copied verbatim from the declaring entity, not an instance name or presumed enclosing entity.
- Realization: each mapping demonstrably stores, sets, computes, or exits the conceptual value. No carrier may be reported as a structural reference.
- Boundary behavior: exit-port claims correspond to outward value flow at that declaring entity.
- Semantic consistency: the conceptual meaning is preserved at each reference; a related but distinct decision is not substituted for the concept.
- State and gating: copied state is not mistaken for mere combinational transport, and transport or enabling is not mislabeled as setting or computing.
- Field granularity: field and aggregate mappings have independent realization evidence.
- Consistency: guards, assignment priorities, reachability, reset behavior, alternate uses, and elaboration conditions do not contradict the claim.
- Completeness: supported concepts and realization points were not omitted merely because another reference already represents the same concept. Do not add upstream dependencies as a substitute for completeness.
- Representation: the JSON uses only the specified keys and allowed realization and objective strings, with proper JSON escaping and no duplicate mappings within a conceptual entry.

When a check fails, correct the claim using existing RTL evidence, narrow it if justified, or remove it if its classification is no longer Established. Do not conceal an evidence gap with a generic security statement.

11. Output representation

The executor returns the EXECUTOR OUTPUT SCHEMA below and nothing else.

“reasoning” provides an evidence-grounded summary of the flow, conceptual meaning, security property, selected objective, and realization basis. It does not expose private chain-of-thought or list rejected candidates. The alternatives shown in the schema are instructions to select an allowed string, not literal JSON syntax to reproduce.

Return ONE JSON object and nothing else: no markdown, no code fences, no prose. Use the keys exactly as written.
{"module name": "<the module analysed>",
 "conceptual assets": [
   {"concept": "<the conceptual asset identified>",
    "security objective": "Confidentiality" | "Integrity" | "Availability",
    "reasoning": "<how it was considered an asset, grounded in the RTL>",
    "related structural assets": [
      {"asset rtl": "<exact declared name from the closed set; a field of an internal record signal is written with its dot, as declared>",
       "entity": "<the entity that declares the element, copied verbatim>",
       "realization": "stores" | "sets" | "computes" | "exit port"}
    ]}
 ]}
If the module has no Established conceptual assets, return {"module name": "<the module analysed>", "conceptual assets": []}.
